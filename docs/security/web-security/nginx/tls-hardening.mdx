# TLS Hardening in Nginx

TLS hardening is about making HTTPS reliable, modern, and maintainable.

For most sites, that means:

- serving correct certificates
- using modern protocol versions
- avoiding cargo-cult cipher strings
- enabling session reuse
- optionally enabling OCSP stapling correctly
- keeping the configuration clear and auditable

This guide keeps the setup practical instead of turning it into a museum of old SSL advice.

## The most important starting point

Modern Nginx already defaults to:

- `ssl_protocols TLSv1.2 TLSv1.3`
- `ssl_ciphers HIGH:!aNULL:!MD5`

That means many old blog posts telling you to paste giant cipher lists are outdated.

You can still configure TLS explicitly for clarity, but you do not need to cargo-cult huge legacy cipher strings into every config.

## Step 1: Build a clean HTTPS server block

```nginx
server {
  listen 443 ssl http2;
  server_name example.com www.example.com;

  ssl_certificate     /etc/letsencrypt/live/example.com/fullchain.pem;
  ssl_certificate_key /etc/letsencrypt/live/example.com/privkey.pem;

  ssl_protocols TLSv1.2 TLSv1.3;

  ssl_session_cache shared:SSL:10m;
  ssl_session_timeout 10m;

  location / {
    proxy_pass http://app_backend;
  }
}
````

## Why this is a good baseline

### `listen 443 ssl`

Use the `ssl` parameter on the `listen` directive.

The old `ssl on;` style is obsolete and removed in current Nginx.

### `ssl_protocols TLSv1.2 TLSv1.3`

This is the modern baseline and also matches current Nginx defaults.

### `ssl_session_cache shared:SSL:10m`

Shared session cache improves TLS session reuse across workers.

### `ssl_session_timeout 10m`

A modest session timeout is a sensible baseline for many sites.

## Step 2: Redirect HTTP to HTTPS

Keep the redirect separate and simple:

```nginx
server {
  listen 80;
  server_name example.com www.example.com;

  return 301 https://$host$request_uri;
}
```

## Step 3: Add OCSP stapling correctly

OCSP stapling is optional, but if you use it, configure it correctly.

```nginx
server {
  listen 443 ssl http2;
  server_name example.com www.example.com;

  ssl_certificate     /etc/letsencrypt/live/example.com/fullchain.pem;
  ssl_certificate_key /etc/letsencrypt/live/example.com/privkey.pem;

  ssl_protocols TLSv1.2 TLSv1.3;

  ssl_session_cache shared:SSL:10m;
  ssl_session_timeout 10m;

  ssl_stapling on;
  ssl_stapling_verify on;

  ssl_trusted_certificate /etc/letsencrypt/live/example.com/chain.pem;
  resolver 1.1.1.1 1.0.0.1 valid=300s;
  resolver_timeout 5s;

  location / {
    proxy_pass http://app_backend;
  }
}
```

### Why the extra directives matter

For OCSP stapling to work properly:

* Nginx needs to know the issuing certificate chain
* and it needs a DNS resolver to resolve the OCSP responder hostname

If those are missing, stapling may not work as expected.

## Step 4: Add HSTS only when ready

HSTS belongs on the HTTPS server only.

```nginx
add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
```

If you have not already added it through your headers snippet, add it only after HTTPS is stable.

## About `ssl_ciphers`

For many deployments, leaving cipher selection to current Nginx defaults is reasonable.

If you do set `ssl_ciphers`, do it intentionally and keep it modern.

Avoid giant copied cipher strings from old tutorials unless you have a very specific compatibility requirement.

## About `ssl_prefer_server_ciphers`

This directive only applies when older SSLv3/TLS protocol behavior makes cipher ordering relevant.

For a modern TLS 1.2/1.3 baseline, it is usually not the headline control people imagine it is.

## Default server note for `ssl_protocols`

If you host multiple TLS sites on the same listener, Nginx documents that `ssl_protocols` should be specified in the **default server**, because protocol negotiation happens before the final SNI-based virtual server config is fully chosen.

## Certificate chain reminders

Use the correct certificate files for your environment.

A very common and clean pattern is:

* `fullchain.pem` for `ssl_certificate`
* `privkey.pem` for `ssl_certificate_key`

If you enable stapling verification, make sure the trusted issuer chain is configured as expected.

## Testing

Validate config:

```bash
sudo nginx -t
```

Reload:

```bash
sudo nginx -s reload
```

Inspect the HTTPS response:

```bash
curl -I https://example.com/
```

Inspect stapling:

```bash
openssl s_client -connect example.com:443 -servername example.com -status
```

## Common mistakes

### Copying huge legacy cipher strings

Most of the time this adds complexity without improving your security posture.

### Enabling HSTS before HTTPS is truly ready

This can create painful recovery scenarios if certificates or subdomains are not under control.

### Forgetting the resolver for OCSP stapling

Stapling needs resolver support when Nginx has to resolve the OCSP responder hostname.

### Mixing old and new TLS advice

A lot of old SSL tutorials predate today’s Nginx defaults and modern TLS expectations.

## A clean practical example

```nginx
server {
  listen 443 ssl http2;
  server_name example.com www.example.com;

  ssl_certificate     /etc/letsencrypt/live/example.com/fullchain.pem;
  ssl_certificate_key /etc/letsencrypt/live/example.com/privkey.pem;

  ssl_protocols TLSv1.2 TLSv1.3;

  ssl_session_cache shared:SSL:10m;
  ssl_session_timeout 10m;

  ssl_stapling on;
  ssl_stapling_verify on;
  ssl_trusted_certificate /etc/letsencrypt/live/example.com/chain.pem;
  resolver 1.1.1.1 1.0.0.1 valid=300s;
  resolver_timeout 5s;

  add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;

  location / {
    proxy_pass http://app_backend;
  }
}
```

## Summary

Good TLS hardening in Nginx is mostly about:

* modern protocol versions
* correct certificates
* session reuse
* optional stapling done properly
* clear HTTPS-only policy

Keep the config short, modern, and understandable.

That is better for both security and long-term maintenance.
