# Password Policies

A good password policy should make accounts safer **without** training users into bad habits.

Old password rules often looked strict, but they pushed people toward predictable behavior:

- reusing passwords
- choosing slightly modified weak passwords
- writing passwords down insecurely
- adding fake complexity that attackers already expect

Modern password policy is simpler and more effective.

## What a strong password policy should do

A modern password policy should:

- require enough length
- allow long passphrases
- block weak and compromised passwords
- support password managers
- avoid unnecessary complexity rules
- avoid forced periodic password changes without evidence of compromise
- work well alongside MFA

## Recommended baseline policy

For most websites, apps, and internal systems, a practical baseline is:

- minimum **15 characters** for password-only authentication
- minimum **8 characters** if the password is only one factor in an MFA flow
- maximum length of at least **64 characters**
- allow spaces
- allow all common printable characters
- allow Unicode if your stack handles it correctly
- do not require mixtures of uppercase, lowercase, numbers, and symbols
- do not require routine password expiration
- reject known weak, common, and compromised passwords

:::tip Better goal
The goal is not to make users create "complicated-looking" passwords.

The goal is to make them create passwords that are hard to guess and easy enough to manage safely.
:::

## Why length matters more than forced complexity

A long password or passphrase is usually more useful than a short password with arbitrary symbol rules.

Examples:

- `Dog!2024` looks complex but is weak
- `purple-lantern-river-window` is much longer and typically stronger

This is why modern guidance favors:

- minimum length
- deny lists or blocklists
- MFA
- password managers

over old composition rules.

## Recommended guidance for users

If users choose their own passwords, guide them toward approaches that are both secure and usable.

Good options include:

- a long unique passphrase
- multiple random words
- a strong password generated by a password manager

Examples of user guidance:

- use a unique password for every account
- avoid names, birthdays, sports teams, and other personal patterns
- use a password manager where possible
- turn on MFA for important accounts

## Support password managers

A modern password policy should work with password managers, not against them.

That means:

- allow paste into password fields
- allow long generated passwords
- avoid strange truncation rules
- avoid hidden composition requirements
- avoid breaking autofill unnecessarily

If your system makes password managers frustrating to use, users will fall back to weaker habits.

## Do not silently truncate passwords

If your system accepts a long password but silently cuts it off behind the scenes, that creates confusion and security risk.

Users should know the password they entered is the password that was actually processed.

If you enforce a maximum length internally, handle it explicitly and safely.

## Block weak and compromised passwords

One of the best controls in a password policy is a deny list.

When users create or change a password, compare it against:

- commonly used passwords
- known breached passwords
- dictionary-style weak choices
- context-specific weak values such as:
  - the service name
  - the username
  - the company name
  - simple variations of those values

Examples to reject:

- `password123`
- `Summer2025!`
- `CompanyName1!`
- `johnsmith2024`
- `qwertyuiop`

:::warning Do not teach users to "just add a symbol"
If `Password1` is rejected, users often try `Password1!`.

That kind of predictable adjustment is exactly why deny lists and better guidance matter.
:::

The example below shows a basic local deny list check. For production, combine this with a breached-password API such as [Have I Been Pwned](https://haveibeenpwned.com/API/v3#PwnedPasswords).

<Tabs>
  <TabItem value="python" label="Python">

```python
import hashlib
import requests

DENY_LIST = {"password123", "qwertyuiop", "welcome1", "letmein"}

def is_password_denied(password: str, username: str, service_name: str) -> bool:
    normalized = password.lower()

    # Block common weak passwords
    if normalized in DENY_LIST:
        return True

    # Block context-specific values
    if username.lower() in normalized or service_name.lower() in normalized:
        return True

    return False

def is_password_pwned(password: str) -> bool:
    """Check against the Have I Been Pwned k-anonymity API."""
    sha1 = hashlib.sha1(password.encode()).hexdigest().upper()
    prefix, suffix = sha1[:5], sha1[5:]

    response = requests.get(f"https://api.pwnedpasswords.com/range/{prefix}")
    return suffix in response.text
```

```js
import crypto from "crypto";

const DENY_LIST = new Set(["password123", "qwertyuiop", "welcome1", "letmein"]);

function isPasswordDenied(password, username, serviceName) {
  const normalized = password.toLowerCase();

  if (DENY_LIST.has(normalized)) return true;
  if (normalized.includes(username.toLowerCase())) return true;
  if (normalized.includes(serviceName.toLowerCase())) return true;

  return false;
}

async function isPasswordPwned(password) {
  const sha1 = crypto.createHash("sha1").update(password).digest("hex").toUpperCase();
  const [prefix, suffix] = [sha1.slice(0, 5), sha1.slice(5)];

  const res = await fetch(`https://api.pwnedpasswords.com/range/${prefix}`);
  const text = await res.text();
  return text.includes(suffix);
}
```

```php
    return str_contains($response, $suffix);
}
```

## Do not require routine password changes

Forced password rotation every 30, 60, or 90 days is often counterproductive when there is no sign of compromise.

It tends to produce behavior like:

- tiny predictable changes
- reused base passwords
- note-taking workarounds
- user frustration without meaningful risk reduction

Change passwords when it makes sense, such as:

- there is evidence of compromise
- credentials were exposed in a breach
- an account recovery flow was abused
- a privileged account was mishandled
- your authentication method or storage model changed significantly

## MFA changes the picture

Passwords are still important, but MFA reduces the impact of password theft.

That means a strong password policy should be paired with:

- MFA for admins
- MFA for staff
- MFA for high-risk users or actions
- phishing-resistant MFA where possible

Password policy works best as part of a broader authentication strategy, not as a standalone defense.

## Different accounts may need different rules

Not every account has the same risk.

### Standard user accounts

A practical baseline is usually enough:

- good minimum length
- block weak passwords
- support password managers
- encourage MFA

### Privileged or admin accounts

Use stricter protection around the account, not necessarily stranger password rules.

Good additional controls include:

- mandatory MFA
- step-up authentication for sensitive actions
- security notifications
- tighter recovery processes
- stronger monitoring and audit logging

## Password creation UX matters

A strong policy can still fail if the user experience is poor.

A good password-change or signup form should:

- clearly state the minimum length
- not force unnecessary symbol rules
- allow paste
- show whether Caps Lock is on where useful
- explain rejections clearly
- avoid vague messages like "invalid password"
- optionally include a strength meter

If a password is rejected, tell the user why in a useful way.

Good example:

> This password is too common or too easy to guess. Try a longer unique passphrase.

Bad example:

> Password invalid.

Below is an example of validation logic that returns user-friendly rejection reasons.

```python
MIN_LENGTH = 15

def validate_password(password: str, username: str, service: str) -> list[str]:
    errors = []

        errors.append(
            "This password has appeared in a known data breach. "
            "Please choose a different one."
        )

    return errors
```

## Example policy statement

Here is a practical community-friendly policy you can publish internally or externally:

> Passwords must be at least 15 characters long unless they are used only as one factor in a multi-factor login flow, in which case the minimum is 8 characters. Passwords may include spaces and common characters. Long passphrases and password-manager-generated passwords are supported. Weak, common, and compromised passwords are blocked. Routine forced password changes are not required unless there is evidence of compromise.

## Recommended implementation controls

A real password policy is more than text in a handbook.

The application should enforce it with controls such as:

- minimum length checks
- weak-password deny lists
- breached-password screening
- rate limiting on login attempts
- MFA support
- secure password reset flow
- audit logging for password changes and resets

## Password resets and recovery

Recovery flows are part of password policy whether people realize it or not.

A strong password policy is weakened immediately if reset flows are weak.

Good reset practices include:

- short-lived reset tokens
- one-time use reset links or codes
- no security questions
- notifications when a reset is requested or completed
- MFA or step-up checks for high-risk accounts
- logging of recovery events

The example below shows a basic short-lived, one-time-use reset token pattern.

<Tabs>
  <TabItem value="python" label="Python">

```python
import secrets
import time

# In production, store tokens in your database, not in memory.
_reset_tokens: dict[str, dict] = {}

RESET_TOKEN_TTL_SECONDS = 900  # 15 minutes

def generate_reset_token(user_id: str) -> str:
    token = secrets.token_urlsafe(32)
    _reset_tokens[token] = {
        "user_id": user_id,
        "expires_at": time.time() + RESET_TOKEN_TTL_SECONDS,
        "used": False,
    }
    return token

def consume_reset_token(token: str) -> str | None:
    """Returns the user_id if the token is valid, otherwise None."""
    entry = _reset_tokens.pop(token, None)
    if not entry:
        return None
    if entry["used"] or time.time() > entry["expires_at"]:
        return None
    return entry["user_id"]
```

```js
import crypto from "crypto";

// In production, store tokens in your database, not in memory.
const resetTokens = new Map();
const RESET_TOKEN_TTL_MS = 15 * 60 * 1000; // 15 minutes

function generateResetToken(userId) {
  const token = crypto.randomBytes(32).toString("hex");
  resetTokens.set(token, {
    userId,
    expiresAt: Date.now() + RESET_TOKEN_TTL_MS,
    used: false,
  });
  return token;
}

function consumeResetToken(token) {
  const entry = resetTokens.get(token);
  resetTokens.delete(token);

  if (!entry || entry.used || Date.now() > entry.expiresAt) return null;
  return entry.userId;
}
```

```php
$resetTokens = [];
const RESET_TOKEN_TTL = 900; // 15 minutes

function generateResetToken(string $userId): string {
    global $resetTokens;
    $token = bin2hex(random_bytes(32));
    $resetTokens[$token] = [
        'user_id'    => $userId,
        'expires_at' => time() + RESET_TOKEN_TTL,
        'used'       => false,
    ];
    return $token;
}

function consumeResetToken(string $token): ?string {
    global $resetTokens;
    $entry = $resetTokens[$token] ?? null;
    unset($resetTokens[$token]);

    if (!$entry || $entry['used'] || time() > $entry['expires_at']) {
        return null;
    }
    return $entry['user_id'];
}
```

## Storage matters too

A password policy is incomplete if passwords are stored badly.

On the server side:

- passwords should be **hashed**, not encrypted, in normal application designs
- use a modern password hashing algorithm
- use unique salts
- upgrade legacy storage over time
- consider additional defense-in-depth measures where appropriate

Your policy for users and your storage design for developers should support each other.

## Recommended storage note for developers

If this page is also read by developers, include a short implementation note like:

- prefer Argon2id where available
- use scrypt if Argon2id is not available
- bcrypt is acceptable for legacy systems with care
- PBKDF2 may be needed in FIPS-focused environments
- never store plaintext passwords
- do not build custom password hashing schemes

```python
from argon2 import PasswordHasher
from argon2.exceptions import VerifyMismatchError

ph = PasswordHasher()

def hash_password(password: str) -> str:
    return ph.hash(password)

def verify_password(stored_hash: str, password: str) -> bool:
    try:
        ph.verify(stored_hash, password)
        # Rehash automatically if parameters have been upgraded
        if ph.check_needs_rehash(stored_hash):
            return True  # caller should rehash and store new hash
        return True
    except VerifyMismatchError:
        return False
```

## Good examples vs bad examples

### Better password choices

- `violet-cable-sunrise-ladder`
- `MarketSilverPlanetWindow`
- password-manager-generated random passwords

### Poor password choices

- `Welcome123`
- `Summer2025!`
- `John1990!`
- `CompanyName1`
- `P@ssw0rd`

## Common mistakes

### Forcing composition rules

This often creates predictable passwords, not strong ones.

### Low maximum length

Artificially small limits punish users who want to use passphrases or password managers.

### Forced rotation without reason

This creates churn, not necessarily better security.

### Blocking paste

This hurts password-manager use and often lowers security.

### No deny list

Without one, users will still choose common and breached passwords.

### Silent truncation

This creates confusing authentication failures and security ambiguity.

### No support for MFA

Passwords should not be carrying the whole burden alone.

## Practical rollout plan

A good modernization path looks like this:

1. remove arbitrary composition rules
2. increase minimum and maximum supported length
3. allow paste and support password managers
4. add breached-password and weak-password blocking
5. remove routine forced password expiration
6. strengthen reset and recovery flows
7. require MFA for privileged accounts
8. review password storage implementation

## Summary

A good password policy is not about making users suffer.

It is about making secure behavior easier and insecure behavior harder.

The strongest modern approach is:

- prioritize length
- support passphrases and password managers
- block weak and compromised passwords
- avoid arbitrary complexity rules
- avoid routine forced resets
- pair passwords with MFA
- store passwords securely on the backend

That gives your users and your systems a much better foundation than old-school password rules ever did.
