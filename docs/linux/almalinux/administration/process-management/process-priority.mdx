# Process Priority

When multiple processes compete for CPU time, the kernel scheduler decides who runs and for how long. By controlling process priority, CPU affinity, and scheduling policies, you can ensure that critical services get the resources they need while background tasks stay out of the way.

## Understanding priority on Linux

Linux uses two separate priority systems:

- **Nice values** — used by the standard CFS (Completely Fair Scheduler) for normal processes
- **Real-time priorities** — used by SCHED_FIFO and SCHED_RR for time-critical processes

### Nice values

Nice values range from **-20** (highest priority) to **+19** (lowest priority). The default is **0**.

```
-20  ← highest priority (less nice to other processes)
  0  ← default
+19  ← lowest priority (very nice to other processes)
```

A lower nice value means the process gets more CPU time relative to others. Only root can set negative nice values.

### Real-time priorities

Real-time priorities range from **1** (lowest) to **99** (highest). Real-time processes always preempt normal processes. Use them carefully — a runaway real-time process can starve everything else.

## View current priority

```bash
# Show nice value for all processes
ps -eo pid,ni,pri,comm --sort=ni | head -20

# Show nice and real-time priority
ps -eo pid,ni,pri,rtprio,comm | head -20

# View priority for a specific process
ps -p $(pgrep nginx | head -1) -o pid,ni,pri,rtprio,comm

# Interactive view with priorities
htop
# Press F2 → Display options → Show custom thread names
```

Column meanings in ps output:

| Column | Meaning |
|--------|---------|
| `NI` | Nice value (-20 to +19) |
| `PRI` | Kernel priority (lower number = higher priority) |
| `RTPRIO` | Real-time priority (blank = not real-time) |

## Start a process with a specific nice value

```bash
# Start with a lower priority (background task)
nice -n 10 /usr/local/bin/backup.sh

# Start with the lowest priority
nice -n 19 /usr/local/bin/indexer.sh

# Start with higher priority (root required for negative values)
sudo nice -n -5 /usr/local/bin/critical-job.sh
```

## Change priority of a running process with renice

```bash
# Lower priority of a running process
renice -n 10 -p $(pgrep backup | head -1)

# Raise priority (requires root for negative values)
sudo renice -n -5 -p $(pgrep myapp | head -1)

# Set priority for all processes owned by a user
sudo renice -n 10 -u jdoe

# Set priority for all processes in a group
sudo renice -n 5 -g $(id -g developers)
```

## Set priority in a systemd unit

For services managed by systemd, set the nice value directly in the unit file so it is applied consistently on every start.

```bash
sudo systemctl edit myapp
```

```ini
[Service]
# Set a lower priority for background services
Nice=10

# Set a higher priority for critical services (root required)
Nice=-5
```

Reload and restart:

```bash
sudo systemctl daemon-reload
sudo systemctl restart myapp
```

## CPU affinity — pin processes to specific cores

CPU affinity restricts a process to run on specific CPU cores. This is useful for:

- isolating latency-sensitive processes from noisy neighbours
- preventing cache thrashing on NUMA systems
- reserving cores for specific workloads

```bash
# View available CPUs
nproc
lscpu | grep "CPU(s)"

# View the current affinity of a process
taskset -p $(pgrep nginx | head -1)

# Pin a process to core 0 only
taskset -c 0 -p $(pgrep nginx | head -1)

# Pin a process to cores 0 and 1
taskset -c 0,1 -p $(pgrep nginx | head -1)

# Pin a process to cores 2 through 5
taskset -c 2-5 -p $(pgrep nginx | head -1)

# Start a new process pinned to specific cores
taskset -c 0,1 /usr/local/bin/myapp
```

### Set CPU affinity in a systemd unit

```bash
sudo systemctl edit myapp
```

```ini
[Service]
# Pin to cores 0 and 1
CPUAffinity=0 1

# Pin to cores 2 through 7
CPUAffinity=2-7
```

## NUMA affinity

On multi-socket servers, NUMA (Non-Uniform Memory Access) topology matters. Processes that access memory on a remote NUMA node incur higher latency.

```bash
# View NUMA topology
numactl --hardware

# Run a process on NUMA node 0, using only node 0 memory
numactl --cpunodebind=0 --membind=0 /usr/local/bin/myapp

# Interleave memory across all nodes (good for throughput, not latency)
numactl --interleave=all /usr/local/bin/myapp

# View NUMA statistics
numastat
numastat -p $(pgrep myapp | head -1)
```

## Real-time scheduling policies

Real-time scheduling is used for time-critical processes that cannot tolerate scheduler latency. Use with care — real-time processes preempt all normal processes.

### SCHED_FIFO — First In, First Out

A SCHED_FIFO process runs until it voluntarily yields, blocks, or is preempted by a higher-priority real-time process. It never yields to normal processes.

```bash
# Set SCHED_FIFO with priority 50
sudo chrt -f 50 /usr/local/bin/realtime-app

# Change the policy of a running process
sudo chrt -f -p 50 $(pgrep realtime-app | head -1)
```

### SCHED_RR — Round Robin

SCHED_RR is like SCHED_FIFO but processes at the same priority share CPU time in round-robin fashion.

```bash
# Set SCHED_RR with priority 30
sudo chrt -r 30 /usr/local/bin/audio-daemon

# View current scheduling policy and priority
chrt -p $(pgrep audio-daemon | head -1)
```

### SCHED_BATCH — Batch processing

SCHED_BATCH is designed for non-interactive batch jobs. It assumes the process is CPU-intensive and deprioritizes it relative to interactive tasks.

```bash
# Set SCHED_BATCH
chrt -b 0 /usr/local/bin/batch-processor.sh
```

### SCHED_IDLE — Lowest possible priority

SCHED_IDLE runs only when no other process needs the CPU — lower than nice +19.

```bash
# Set SCHED_IDLE
chrt -i 0 /usr/local/bin/background-indexer.sh
```

### Set scheduling policy in a systemd unit

```bash
sudo systemctl edit myapp
```

```ini
[Service]
# SCHED_FIFO with priority 50
CPUSchedulingPolicy=fifo
CPUSchedulingPriority=50

# SCHED_RR with priority 30
CPUSchedulingPolicy=rr
CPUSchedulingPriority=30

# SCHED_BATCH
CPUSchedulingPolicy=batch

# SCHED_IDLE
CPUSchedulingPolicy=idle

# Inherit scheduling policy on exec (prevents child processes from escalating)
CPUSchedulingResetOnFork=yes
```

## I/O priority

I/O scheduling priority controls how the kernel prioritizes disk I/O for a process. This is separate from CPU priority.

```bash
# View current I/O priority
ionice -p $(pgrep nginx | head -1)
```

### I/O scheduling classes

| Class | Meaning |
|-------|---------|
| `0` (none) | Inherits CPU nice value |
| `1` (realtime) | Highest I/O priority — gets I/O first |
| `2` (best-effort) | Default — priority 0-7 (0 = highest) |
| `3` (idle) | Only gets I/O when no other process needs it |

```bash
# Set idle I/O class for a backup job
ionice -c 3 /usr/local/bin/backup.sh

# Set best-effort class with priority 2
ionice -c 2 -n 2 /usr/local/bin/myapp

# Change I/O priority of a running process
ionice -c 3 -p $(pgrep backup | head -1)

# Set real-time I/O priority (root required)
sudo ionice -c 1 -n 0 -p $(pgrep database | head -1)
```

### Set I/O priority in a systemd unit

```bash
sudo systemctl edit myapp
```

```ini
[Service]
# Idle I/O — background tasks
IOSchedulingClass=idle

# Best-effort with priority 4
IOSchedulingClass=best-effort
IOSchedulingPriority=4
```

## Practical priority configurations

### Web server — slightly elevated

```ini
[Service]
Nice=-2
CPUWeight=150
IOSchedulingClass=best-effort
IOSchedulingPriority=2
```

### Database — high priority

```ini
[Service]
Nice=-10
CPUWeight=300
IOSchedulingClass=best-effort
IOSchedulingPriority=0
CPUAffinity=0-3
```

### Backup job — lowest priority

```ini
[Service]
Nice=19
CPUSchedulingPolicy=batch
IOSchedulingClass=idle
CPUWeight=20
```

### Log shipper — background, non-intrusive

```ini
[Service]
Nice=15
IOSchedulingClass=idle
CPUWeight=30
MemoryMax=128M
```

## Scripted priority adjustment

A script to automatically lower the priority of processes that exceed a CPU threshold:

```bash
#!/bin/bash
# auto-renice.sh — lower priority of CPU-hungry background processes

CPU_THRESHOLD=80
NICE_VALUE=15
EXEMPT_USERS="root"

ps aux --sort=-%cpu | tail -n +2 | while read -r user pid cpu mem vsz rss tty stat start time cmd; do
  # Skip exempt users
  echo "$EXEMPT_USERS" | grep -qw "$user" && continue

  # Skip processes already reniced
  CURRENT_NICE=$(ps -p "$pid" -o ni= 2>/dev/null | tr -d ' ')
  [[ "$CURRENT_NICE" -ge "$NICE_VALUE" ]] && continue

  CPU_INT=${cpu%.*}
  if [[ "$CPU_INT" -gt "$CPU_THRESHOLD" ]]; then
    renice -n "$NICE_VALUE" -p "$pid" 2>/dev/null
    echo "$(date '+%F %T') Reniced PID $pid ($cmd) owned by $user from $CURRENT_NICE to $NICE_VALUE (CPU: ${cpu}%)"
  fi
done
```

Schedule with cron:

```bash
sudo crontab -e
```

```
*/2 * * * * /usr/local/bin/auto-renice.sh >> /var/log/auto-renice.log 2>&1
```

## Common mistakes

### Using real-time scheduling for non-time-critical processes

A runaway SCHED_FIFO process with high priority can starve all normal processes, making the system unresponsive.

```bash
# Always set a reasonable priority — never use 99
sudo chrt -f 20 /usr/local/bin/myapp
```

### Setting nice values without ionice for I/O-heavy jobs

A backup job with nice +19 will still compete for I/O if ionice is not also set.

```bash
# Set both CPU and I/O priority together
nice -n 19 ionice -c 3 /usr/local/bin/backup.sh
```

### Pinning too many processes to the same core

CPU affinity is powerful but over-pinning concentrates load and wastes other cores.

```bash
# Check current core utilisation before pinning
mpstat -P ALL 1 3
```

### Not using CPUSchedulingResetOnFork

Without this, child processes spawned by a real-time service inherit the real-time scheduling policy — which may not be intended.

```ini
[Service]
CPUSchedulingResetOnFork=yes
```

## Summary

Process priority on AlmaLinux covers three dimensions — CPU scheduling priority, CPU core affinity, and I/O scheduling priority. Used together through systemd unit directives, they give you fine-grained control over how workloads compete for resources.

Key points:

- use `nice` and `renice` for quick priority adjustments on normal processes
- set `Nice=` in systemd unit files for persistent, consistent priority
- use `taskset` or `CPUAffinity=` to pin latency-sensitive processes to specific cores
- use `ionice -c 3` or `IOSchedulingClass=idle` for background I/O tasks
- use real-time scheduling only for genuinely time-critical processes — and never at priority 99
- combine nice and ionice for CPU and I/O bound background jobs
- use `CPUSchedulingResetOnFork=yes` to prevent child processes from inheriting real-time policies
