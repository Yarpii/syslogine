# Resource Controls

Without resource controls, a single runaway process can consume all available CPU, memory, or I/O and bring down everything else running on the system. AlmaLinux uses **cgroups v2** (control groups) as the foundation for resource management, and systemd exposes cgroup controls directly through unit file configuration — no manual cgroup wiring required.

## How cgroups v2 works on AlmaLinux

cgroups v2 organizes processes into a hierarchy. Each systemd service runs in its own cgroup slice, and resource limits applied to a cgroup affect all processes within it.

```
system.slice
  ├── nginx.service
  ├── postgresql.service
  └── myapp.service

user.slice
  └── user-1000.slice
      └── session-1.scope
```

```bash
# View the full cgroup hierarchy
systemd-cgls

# View resource usage per cgroup
systemd-cgtop

# View which cgroup a process belongs to
cat /proc/$(pgrep nginx | head -1)/cgroup
```

## Set resource limits on a systemd service

The cleanest way to apply resource controls on AlmaLinux is through systemd unit overrides. This keeps limits persistent and version-controllable.

```bash
sudo systemctl edit nginx
```

This opens a drop-in override file at `/etc/systemd/system/nginx.service.d/override.conf`.

### Memory limits

```ini
[Service]
# Hard memory limit — processes are killed if this is exceeded
MemoryMax=512M

# Soft memory limit — kernel tries to keep usage below this
MemoryHigh=400M

# Memory the service is guaranteed to get
MemoryMin=64M

# Swap limit (requires MemoryMax)
MemorySwapMax=0
```

### CPU limits

```ini
[Service]
# Percentage of one CPU core (100% = 1 core, 200% = 2 cores)
CPUQuota=150%

# Relative CPU weight (default 100, higher = more CPU time)
CPUWeight=80

# Absolute CPU time allowed per period
CPUAccounting=yes
```

### I/O limits

```ini
[Service]
# Limit read throughput on a device
IOReadBandwidthMax=/dev/sda 50M

# Limit write throughput
IOWriteBandwidthMax=/dev/sda 50M

# Limit read IOPS
IOReadIOPSMax=/dev/sda 1000

# Limit write IOPS
IOWriteIOPSMax=/dev/sda 1000

# Relative I/O weight (default 100)
IOWeight=50
```

### Task and file descriptor limits

```ini
[Service]
# Maximum number of processes and threads
TasksMax=256

# Maximum open file descriptors
LimitNOFILE=65536

# Maximum core dump size (0 = disable core dumps)
LimitCORE=0

# Maximum number of open files system-wide for this service
LimitNOFILESoft=32768
```

After editing, reload and restart:

```bash
sudo systemctl daemon-reload
sudo systemctl restart nginx
```

Verify limits are applied:

```bash
systemctl show nginx | grep -E "Memory|CPU|IO|Tasks|Limit"
```

## Apply limits to all services in a slice

Slices group related services. Limits on a slice apply to the total resource usage of all services within it.

```bash
sudo systemctl edit system.slice
```

```ini
[Slice]
# Total memory limit for all system services combined
MemoryMax=8G

# Total CPU weight for system services
CPUWeight=800
```

Create a custom slice for a group of related services:

```bash
sudo nano /etc/systemd/system/webstack.slice
```

```ini
[Unit]
Description=Web Stack Services Slice
Before=slices.target

[Slice]
MemoryMax=2G
CPUQuota=400%
IOWeight=200
```

Then assign services to the slice:

```bash
sudo systemctl edit nginx
```

```ini
[Service]
Slice=webstack.slice
```

```bash
sudo systemctl daemon-reload
```

## Set per-user resource limits with pam_limits

For interactive users, `pam_limits` enforces resource limits at login time via `/etc/security/limits.conf`.

```bash
sudo nano /etc/security/limits.conf
```

```ini
# Syntax: domain  type  item  value

# Limit all users to 4096 open files (soft) and 65536 (hard)
*         soft  nofile    4096
*         hard  nofile    65536

# Limit a specific user's processes
jdoe      soft  nproc     512
jdoe      hard  nproc     1024

# Limit a group's memory lock
@developers soft  memlock   unlimited
@developers hard  memlock   unlimited

# Restrict max login sessions
contractor1  hard  maxlogins  2

# Disable core dumps for all users
*         hard  core      0
```

Add per-service limits in `/etc/security/limits.d/`:

```bash
sudo nano /etc/security/limits.d/nginx.conf
```

```ini
nginx     soft  nofile    65536
nginx     hard  nofile    65536
nginx     soft  nproc     512
nginx     hard  nproc     512
```

## Set kernel-level resource parameters with sysctl

Some resource limits are set at the kernel level via `sysctl`.

```bash
sudo nano /etc/sysctl.d/99-resource-limits.conf
```

```ini
# Maximum open file descriptors system-wide
fs.file-max = 2097152

# Maximum inotify watches per user
fs.inotify.max_user_watches = 524288

# Maximum number of memory map areas per process
vm.max_map_count = 262144

# Kernel panic on OOM if no process can be killed
vm.panic_on_oom = 0

# OOM killer behaviour (0 = kill least costly process)
vm.oom_kill_allocating_task = 0

# Swappiness — how aggressively to use swap (0-100)
vm.swappiness = 10
```

Apply immediately:

```bash
sudo sysctl --system
```

## Monitor cgroup resource usage

```bash
# Live resource usage per service
systemd-cgtop

# Memory usage for a specific service
cat /sys/fs/cgroup/system.slice/nginx.service/memory.current

# CPU usage for a specific service
cat /sys/fs/cgroup/system.slice/nginx.service/cpu.stat

# I/O stats for a specific service
cat /sys/fs/cgroup/system.slice/nginx.service/io.stat

# Current tasks count
cat /sys/fs/cgroup/system.slice/nginx.service/pids.current
```

## Prevent a service from being OOM killed

The OOM killer scores processes and kills the highest scorer when memory is exhausted. You can protect critical services.

```bash
sudo systemctl edit nginx
```

```ini
[Service]
# Lower OOM score adjustment — less likely to be killed (-1000 = never kill)
OOMScoreAdjust=-500
```

Or protect a specific PID manually:

```bash
# Set OOM score for a running process (-1000 = protected)
echo -500 | sudo tee /proc/$(pgrep nginx | head -1)/oom_score_adj
```

## Temporary resource limits with systemd-run

`systemd-run` launches a command in a transient systemd unit with resource limits — useful for one-off jobs without creating permanent unit files.

```bash
# Run a backup script with memory and CPU limits
sudo systemd-run \
  --unit=backup-job \
  --property=MemoryMax=512M \
  --property=CPUQuota=50% \
  --property=IOWriteBandwidthMax="/dev/sda 20M" \
  /usr/local/bin/backup.sh

# Run interactively in a limited shell
sudo systemd-run \
  --shell \
  --property=MemoryMax=256M \
  --property=CPUQuota=25%

# Check the transient unit
systemctl status backup-job
journalctl -u backup-job
```

## Enforce limits on containers and services with resource accounting

Enable accounting for accurate per-service metrics:

```bash
sudo nano /etc/systemd/system.conf
```

```ini
[Manager]
DefaultCPUAccounting=yes
DefaultMemoryAccounting=yes
DefaultIOAccounting=yes
DefaultTasksAccounting=yes
```

Restart systemd (takes effect on next boot, or reload):

```bash
sudo systemctl daemon-reexec
```

## Scripted resource limit verification

A script to check whether critical services are running within their defined limits:

```bash
#!/bin/bash
# check-resource-limits.sh — verify services are within limits

SERVICES=("nginx" "postgresql" "redis")
ALERT_EMAIL="ops@example.com"
HOSTNAME=$(hostname)
ALERTS=()

for service in "${SERVICES[@]}"; do
  CGROUP="/sys/fs/cgroup/system.slice/${service}.service"

  [[ ! -d "$CGROUP" ]] && continue

  # Check memory
  MEM_CURRENT=$(cat "${CGROUP}/memory.current" 2>/dev/null || echo 0)
  MEM_MAX=$(cat "${CGROUP}/memory.max" 2>/dev/null || echo "max")

  if [[ "$MEM_MAX" != "max" && "$MEM_CURRENT" -gt 0 ]]; then
    MEM_PCT=$(( MEM_CURRENT * 100 / MEM_MAX ))
    if [[ "$MEM_PCT" -gt 90 ]]; then
      MEM_MB=$(( MEM_CURRENT / 1024 / 1024 ))
      MEM_MAX_MB=$(( MEM_MAX / 1024 / 1024 ))
      ALERTS+=("HIGH MEMORY: $service using ${MEM_MB}MB of ${MEM_MAX_MB}MB limit (${MEM_PCT}%)")
    fi
  fi

  # Check task count
  TASKS_CURRENT=$(cat "${CGROUP}/pids.current" 2>/dev/null || echo 0)
  TASKS_MAX=$(cat "${CGROUP}/pids.max" 2>/dev/null || echo "max")

  if [[ "$TASKS_MAX" != "max" && "$TASKS_CURRENT" -gt 0 ]]; then
    TASKS_PCT=$(( TASKS_CURRENT * 100 / TASKS_MAX ))
    if [[ "$TASKS_PCT" -gt 85 ]]; then
      ALERTS+=("HIGH TASKS: $service using $TASKS_CURRENT of $TASKS_MAX tasks (${TASKS_PCT}%)")
    fi
  fi
done

if [[ "${#ALERTS[@]}" -gt 0 ]]; then
  MESSAGE="Resource limit alert on ${HOSTNAME}:\n\n$(printf '%s\n' "${ALERTS[@]}")"
  echo -e "$MESSAGE" | mail -s "Resource Limit Alert: ${HOSTNAME}" "$ALERT_EMAIL"
  echo -e "$MESSAGE"
fi
```

Schedule with cron:

```bash
sudo crontab -e
```

```
*/5 * * * * /usr/local/bin/check-resource-limits.sh >> /var/log/resource-limits.log 2>&1
```

## Common mistakes

### Setting MemoryMax without MemoryHigh

`MemoryMax` is a hard limit — processes are killed when it is hit. `MemoryHigh` is a soft limit that triggers reclaim before things get critical. Use both.

```ini
[Service]
MemoryHigh=400M
MemoryMax=512M
```

### Setting CPUQuota=100% and expecting it to use one full core

`CPUQuota=100%` means 100% of one CPU core. On a 4-core system, the service can still be throttled if all cores are busy. Use `CPUWeight` for proportional fairness instead.

### Forgetting daemon-reload after changes

Unit file changes are not picked up until systemd is reloaded.

```bash
sudo systemctl daemon-reload
sudo systemctl restart servicename
```

### Not enabling accounting before measuring

Without `CPUAccounting=yes` and `MemoryAccounting=yes`, cgroup metrics are not collected for that service.

```ini
[Service]
CPUAccounting=yes
MemoryAccounting=yes
IOAccounting=yes
```

### Using pam_limits for services instead of systemd

`pam_limits` only applies to processes started through PAM (interactive logins). For daemons managed by systemd, use unit file limits instead.

## Summary

Resource controls on AlmaLinux are cleanest when applied through systemd unit overrides. cgroups v2 enforces limits reliably at the kernel level, and systemd handles the wiring automatically.

Key points:

- use `systemctl edit servicename` to apply resource limits without modifying the original unit file
- set both `MemoryHigh` and `MemoryMax` — soft and hard limits work better together
- use slices to apply limits to groups of related services
- use `systemd-run` for one-off jobs that need temporary resource limits
- enable CPU, memory, and I/O accounting to get accurate per-service metrics
- use `OOMScoreAdjust` to protect critical services from the OOM killer
- monitor cgroup usage with `systemd-cgtop` and the cgroup filesystem directly
