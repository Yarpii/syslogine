# Service Management

On AlmaLinux, systemd is the init system and service manager. Every daemon, background job, mount point, and scheduled task is represented as a systemd unit. Understanding how to create, configure, and manage units gives you precise control over how services start, stop, restart, and interact with each other.

## Basic service operations

```bash
# Start a service
sudo systemctl start nginx

# Stop a service
sudo systemctl stop nginx

# Restart a service
sudo systemctl restart nginx

# Reload configuration without restarting
sudo systemctl reload nginx

# Reload if supported, restart if not
sudo systemctl reload-or-restart nginx

# Enable at boot
sudo systemctl enable nginx

# Disable at boot
sudo systemctl disable nginx

# Enable and start in one step
sudo systemctl enable --now nginx

# Disable and stop in one step
sudo systemctl disable --now nginx
```

## Inspect service status

```bash
# Full status with recent log output
systemctl status nginx

# Is the service currently running?
systemctl is-active nginx

# Is the service enabled at boot?
systemctl is-enabled nginx

# Has the service failed?
systemctl is-failed nginx

# Show all properties of a service
systemctl show nginx

# Show a specific property
systemctl show nginx --property=MainPID
systemctl show nginx --property=ActiveState
systemctl show nginx --property=FragmentPath
```

## List and filter units

```bash
# All active services
systemctl list-units --type=service --state=active

# All failed units
systemctl list-units --state=failed

# All enabled services
systemctl list-unit-files --type=service --state=enabled

# All services including inactive
systemctl list-units --type=service --all

# Search for a unit by name
systemctl list-units --type=service | grep nginx
```

## Unit file locations

| Location | Purpose |
|----------|---------|
| `/usr/lib/systemd/system/` | Package-provided unit files — do not edit directly |
| `/etc/systemd/system/` | Administrator unit files — take precedence |
| `/run/systemd/system/` | Runtime unit files — lost on reboot |
| `/etc/systemd/system/*.d/` | Drop-in override directories |

Always place custom units and overrides in `/etc/systemd/system/`.

## Anatomy of a service unit file

```ini
[Unit]
Description=My Application Service
Documentation=https://example.com/docs
After=network.target postgresql.service
Requires=postgresql.service
Wants=redis.service

[Service]
Type=simple
User=myapp
Group=myapp
WorkingDirectory=/opt/myapp
EnvironmentFile=/etc/myapp/env
ExecStartPre=/usr/local/bin/myapp-preflight.sh
ExecStart=/usr/local/bin/myapp --config /etc/myapp/config.yml
ExecReload=/bin/kill -HUP $MAINPID
ExecStopPost=/usr/local/bin/myapp-cleanup.sh

Restart=on-failure
RestartSec=5
StartLimitIntervalSec=60
StartLimitBurst=3

StandardOutput=journal
StandardError=journal
SyslogIdentifier=myapp

[Install]
WantedBy=multi-user.target
```

## Service types

The `Type=` directive tells systemd how the service signals that it is ready.

| Type | When to use |
|------|------------|
| `simple` | Default. Process started by `ExecStart` is the main process |
| `exec` | Like simple, but systemd waits for the exec to complete |
| `forking` | Service forks and the parent exits — traditional daemons |
| `oneshot` | Process runs and exits — systemd waits for it to finish |
| `notify` | Service sends `sd_notify()` when ready |
| `dbus` | Service signals readiness via D-Bus |
| `idle` | Like simple, but delayed until other jobs finish |

```ini
# For a traditional daemon that forks
Type=forking
PIDFile=/run/myapp/myapp.pid

# For a script that runs and exits
Type=oneshot
RemainAfterExit=yes

# For a modern daemon using sd_notify
Type=notify
```

## Restart policies

```ini
[Service]
# Restart on failure only
Restart=on-failure

# Always restart (except on clean stop)
Restart=always

# Never restart
Restart=no

# Restart on failure, abnormal exit, watchdog, or on-abort
Restart=on-abnormal

# Seconds to wait before restarting
RestartSec=5

# Maximum restart attempts in a time window
StartLimitIntervalSec=120
StartLimitBurst=5
```

:::tip
`Restart=on-failure` with `StartLimitBurst=5` and `StartLimitIntervalSec=120` is a safe default for most production services. It retries up to 5 times in 2 minutes before giving up — preventing infinite restart loops.
:::

## Create a custom service unit

```bash
sudo nano /etc/systemd/system/myapp.service
```

```ini
[Unit]
Description=My Application
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=myapp
Group=myapp
WorkingDirectory=/opt/myapp
ExecStart=/opt/myapp/bin/myapp
Restart=on-failure
RestartSec=5
StartLimitBurst=5
StartLimitIntervalSec=60

# Security hardening
NoNewPrivileges=yes
ProtectSystem=strict
ProtectHome=yes
PrivateTmp=yes
ReadWritePaths=/var/lib/myapp /var/log/myapp

[Install]
WantedBy=multi-user.target
```

Enable and start it:

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now myapp
sudo systemctl status myapp
```

## Override an existing unit file

Never edit files in `/usr/lib/systemd/system/` directly — package updates will overwrite your changes. Use drop-in overrides instead.

```bash
# Open the override editor
sudo systemctl edit nginx
```

This creates `/etc/systemd/system/nginx.service.d/override.conf`. Add only the directives you want to change:

```ini
[Service]
# Add an environment variable
Environment=NGINX_WORKERS=4

# Change the restart policy
Restart=always
RestartSec=3

# Add a resource limit
MemoryMax=512M
```

To replace the entire unit:

```bash
sudo systemctl edit --full nginx
```

This copies the unit to `/etc/systemd/system/nginx.service` for full editing.

View what overrides are active:

```bash
systemctl cat nginx
```

## Service dependencies

Systemd manages service ordering and dependencies through unit directives.

| Directive | Meaning |
|-----------|---------|
| `After=` | Start after these units (ordering only) |
| `Before=` | Start before these units (ordering only) |
| `Requires=` | Hard dependency — if this fails, this unit fails too |
| `Wants=` | Soft dependency — start this if possible, continue if not |
| `BindsTo=` | Like Requires, but also stops this unit if the dependency stops |
| `Conflicts=` | Cannot run at the same time as these units |
| `PartOf=` | Stop/restart this unit when the listed unit stops/restarts |

```ini
[Unit]
# Start after the network and database are ready
After=network-online.target postgresql.service

# Hard dependency — fail if postgresql is not running
Requires=postgresql.service

# Soft dependency — start redis if available
Wants=redis.service

# Stop this service if nginx stops
PartOf=nginx.service
```

## Environment variables and files

```ini
[Service]
# Inline environment variable
Environment=APP_ENV=production
Environment=PORT=8080

# Load variables from a file
EnvironmentFile=/etc/myapp/env
EnvironmentFile=-/etc/myapp/env.local
```

The `-` prefix means the file is optional — systemd will not fail if it does not exist.

Example environment file:

```bash
# /etc/myapp/env
APP_ENV=production
DB_HOST=localhost
DB_PORT=5432
LOG_LEVEL=info
```

## Templated units

Templated units let you run multiple instances of the same service with different parameters.

```bash
sudo nano /etc/systemd/system/worker@.service
```

```ini
[Unit]
Description=Worker instance %i
After=network.target

[Service]
Type=simple
User=myapp
ExecStart=/opt/myapp/bin/worker --queue %i
Restart=on-failure

[Install]
WantedBy=multi-user.target
```

Start named instances:

```bash
sudo systemctl enable --now worker@emails
sudo systemctl enable --now worker@images
sudo systemctl enable --now worker@reports

# Check all instances
systemctl status 'worker@*'
```

The `%i` specifier is replaced with the instance name at runtime.

## Oneshot services for startup tasks

A oneshot service runs a command once and exits. Useful for initialization tasks, database migrations, or setup scripts that should run at boot.

```bash
sudo nano /etc/systemd/system/db-migrate.service
```

```ini
[Unit]
Description=Run database migrations
After=postgresql.service
Requires=postgresql.service
Before=myapp.service

[Service]
Type=oneshot
User=myapp
ExecStart=/opt/myapp/bin/migrate --run
RemainAfterExit=yes

[Install]
WantedBy=multi-user.target
```

```bash
sudo systemctl enable db-migrate
```

## Service watchdog

The systemd watchdog kills and restarts a service if it stops responding within a timeout.

```ini
[Service]
# Kill and restart if the service does not ping the watchdog within 30 seconds
WatchdogSec=30

# The service must call sd_notify("WATCHDOG=1") periodically
Type=notify
```

For services that do not support sd_notify natively, use a wrapper:

```bash
sudo nano /etc/systemd/system/myapp.service
```

```ini
[Service]
ExecStartPost=/bin/sh -c 'while kill -0 $MAINPID 2>/dev/null; do systemd-notify WATCHDOG=1; sleep 10; done &'
WatchdogSec=30
```

## View service logs

```bash
# All logs for a service
journalctl -u nginx

# Follow logs in real time
journalctl -u nginx -f

# Logs since last boot
journalctl -u nginx -b

# Logs for the last hour
journalctl -u nginx --since "1 hour ago"

# Only errors
journalctl -u nginx -p err

# Logs for multiple services
journalctl -u nginx -u php-fpm -f
```

## Common mistakes

### Editing unit files in /usr/lib/systemd/system/

Package updates silently overwrite these files. Always use `systemctl edit` for overrides.

```bash
# WRONG
sudo nano /usr/lib/systemd/system/nginx.service

# CORRECT
sudo systemctl edit nginx
```

### Forgetting daemon-reload after changes

```bash
sudo systemctl daemon-reload
sudo systemctl restart myapp
```

### Using Requires= when Wants= is more appropriate

`Requires=` causes your service to fail if the dependency is not available. For optional dependencies, `Wants=` is safer.

### Setting Restart=always without StartLimitBurst

Without a restart limit, a service that fails immediately on start will restart in an infinite loop, consuming resources.

```ini
[Service]
Restart=always
RestartSec=5
StartLimitIntervalSec=120
StartLimitBurst=5
```

### Not using PrivateTmp and ProtectSystem for new services

These directives are free security hardening. Always include them for custom services.

```ini
[Service]
NoNewPrivileges=yes
ProtectSystem=strict
ProtectHome=yes
PrivateTmp=yes
```

## Summary

systemd service management on AlmaLinux is clean and consistent once you understand unit files, overrides, and dependency directives. Well-configured services start reliably, restart gracefully on failure, and stay within their resource boundaries.

Key points:

- use `systemctl edit` for overrides — never touch `/usr/lib/systemd/system/`
- always run `systemctl daemon-reload` after creating or editing unit files
- set `Restart=on-failure` with `StartLimitBurst` to prevent infinite restart loops
- use `After=` and `Wants=` for ordering and soft dependencies, `Requires=` only for hard ones
- use `EnvironmentFile=` to keep configuration out of unit files
- use templated units (`@`) to run multiple instances of the same service
- add `NoNewPrivileges`, `ProtectSystem`, and `PrivateTmp` to all custom service units
