# Enterprise Scheduling on AlmaLinux

Simple cron entries and basic systemd timers cover the majority of scheduling needs. But as environments grow more complex — more servers, more interdependent jobs, stricter reliability requirements — gaps appear. What happens when two instances of the same job run simultaneously? How do you ensure job B does not start until job A has completed successfully? How do you handle transient failures gracefully without waking someone up at 03:00? How do you schedule work across multiple servers without duplication?

Enterprise scheduling addresses these problems with patterns and techniques that go beyond a simple time-triggered command. This page covers the most important of these: job locking to prevent concurrent execution, dependency chains between jobs, retry logic and error handling, parallel execution with coordination, and integration with external automation platforms.

---

## Preventing Concurrent Job Execution with flock

The most common scheduling problem in production environments is a job that takes longer than its scheduling interval. If a backup job is scheduled every hour but occasionally takes 90 minutes, two instances will overlap. Two instances writing to the same archive or reading from the same database simultaneously can produce corruption, incorrect results, or failures that are difficult to diagnose.

`flock` acquires a file lock before running a command and releases it when the command exits. A second instance attempting to acquire the same lock while the first is running either waits or exits immediately, depending on configuration — preventing concurrent execution.

### Basic flock Usage

To run a script with exclusive locking, using a lock file in `/var/lock/`:

```bash
flock -n /var/lock/my-job.lock /usr/local/sbin/my-job.sh
```

The `-n` flag (non-blocking) causes `flock` to exit immediately with a non-zero status if the lock cannot be acquired, rather than waiting. This is appropriate for scheduled jobs — if the previous run is still active, skip this run rather than queuing behind it.

In a crontab entry:

```
0 * * * *  root  flock -n /var/lock/my-job.lock /usr/local/sbin/my-job.sh
```

### flock with Logging

The bare `flock -n` command exits silently if the lock is not available. For scheduled jobs where you want to know that a run was skipped, add logging:

```bash
nano /usr/local/sbin/run-locked.sh
```

```bash
#!/bin/bash
# run-locked.sh
# Wrapper that runs a command with exclusive locking, logging skipped runs.
# Usage: run-locked.sh <lockfile> <command> [args...]

LOCKFILE="$1"
shift
COMMAND="$@"
LOGFILE="/var/log/scheduling/locks.log"

mkdir -p "$(dirname "${LOGFILE}")"
log() { echo "[$(date '+%Y-%m-%d %H:%M:%S')] $*" | tee -a "${LOGFILE}"; }

(
    flock -n 200 || {
        log "SKIPPED: ${COMMAND} — lock held by another instance (${LOCKFILE})"
        exit 0
    }
    log "STARTED: ${COMMAND}"
    eval "${COMMAND}"
    EXIT_CODE=$?
    log "FINISHED: ${COMMAND} (exit code: ${EXIT_CODE})"
    exit "${EXIT_CODE}"
) 200>"${LOCKFILE}"
```

```bash
chmod 700 /usr/local/sbin/run-locked.sh
```

Use it in crontab entries:

```
0 * * * *  root  /usr/local/sbin/run-locked.sh /var/lock/backup.lock /usr/local/sbin/system-backup.sh
```

The file descriptor `200` is used for the lock — a convention that avoids interfering with the standard file descriptors (0, 1, 2). The subshell `( ... ) 200>"${LOCKFILE}"` opens the lock file on descriptor 200 for the duration of the subshell, and `flock -n 200` attempts to lock that descriptor.

### flock in systemd Services

For systemd-timer-driven services, the equivalent of `flock` is the `ExecCondition=` directive combined with a condition check, or more simply, setting `Type=oneshot` with appropriate timeout handling. However, systemd also provides its own locking mechanism: if a service is still running when the timer fires again, systemd will not start a second instance of the service — it simply skips the activation. This is the default behavior for `Type=oneshot` services activated by a timer.

Verify this behavior is active by checking that the service does not have `--no-block` or multiple `ExecStart=` lines that could overlap:

```bash
systemctl show myapp-job.service | grep -E "Type|RemainAfterExit"
```

`Type=oneshot` with `RemainAfterExit=no` (the default) means systemd considers the service inactive as soon as it exits, and the timer can activate it again on the next cycle.

## Job Dependencies and Sequencing

### Sequential Jobs with systemd

Systemd's dependency system allows precise sequencing of jobs without relying on timing assumptions. If job B must always run after job A completes successfully, express this as a unit dependency rather than just scheduling B 30 minutes after A.

Create an intermediate service that activates job B when job A finishes:

```bash
nano /etc/systemd/system/job-a.service
```

```ini
[Unit]
Description=Job A — data import
OnSuccess=job-b.service

[Service]
Type=oneshot
ExecStart=/usr/local/sbin/job-a.sh
```

```bash
nano /etc/systemd/system/job-b.service
```

```ini
[Unit]
Description=Job B — post-import processing
After=job-a.service

[Service]
Type=oneshot
ExecStart=/usr/local/sbin/job-b.sh
```

`OnSuccess=job-b.service` in job A's unit causes systemd to activate job B when job A exits with a zero status. If job A fails (non-zero exit), job B is not activated. This is exactly the behaviour needed for dependent jobs — job B only runs if its prerequisite succeeded.

### Sequential Jobs with Shell Chaining

For simpler dependency chains where both jobs run as part of the same logical task, chain them in a single script using `&&`:

```bash
#!/bin/bash
# pipeline.sh
# Runs a three-stage pipeline where each stage depends on the previous.

/usr/local/sbin/stage1-extract.sh \
    && /usr/local/sbin/stage2-transform.sh \
    && /usr/local/sbin/stage3-load.sh \
    || {
        echo "Pipeline failed at $(date)" \
            | mail -s "Pipeline Failure" admin@example.com
        exit 1
    }
```

The `&&` operator short-circuits — if any stage fails, subsequent stages are skipped and the error handler runs. This is simpler than systemd dependencies for jobs that always run together and do not need to be individually scheduled.

### Fan-Out and Fan-In: Parallel Jobs with Coordination

Some workflows involve running multiple independent jobs in parallel and then doing something when all of them complete. Shell's background execution and `wait` handle this pattern:

```bash
nano /usr/local/sbin/parallel-backup.sh
```

```bash
#!/bin/bash
# parallel-backup.sh
# Backs up multiple databases in parallel and waits for all to complete.

LOGFILE="/var/log/backup/parallel.log"
ALERT_EMAIL="admin@example.com"
HOSTNAME=$(hostname -s)

mkdir -p "$(dirname "${LOGFILE}")"
log() { echo "[$(date '+%Y-%m-%d %H:%M:%S')] $*" | tee -a "${LOGFILE}"; }

log "Starting parallel database backups"

# Start all backup jobs in the background, capturing their PIDs
/usr/local/sbin/backup-db.sh customerdb &
PID_CUSTOMER=$!

/usr/local/sbin/backup-db.sh analyticsdb &
PID_ANALYTICS=$!

/usr/local/sbin/backup-db.sh archivedb &
PID_ARCHIVE=$!

# Wait for each job and collect exit codes
FAILED=0

wait "${PID_CUSTOMER}"; EXIT_CUSTOMER=$?
wait "${PID_ANALYTICS}"; EXIT_ANALYTICS=$?
wait "${PID_ARCHIVE}"; EXIT_ARCHIVE=$?

[[ "${EXIT_CUSTOMER}" -ne 0 ]] && { log "FAILED: customerdb backup"; ((FAILED++)); }
[[ "${EXIT_ANALYTICS}" -ne 0 ]] && { log "FAILED: analyticsdb backup"; ((FAILED++)); }
[[ "${EXIT_ARCHIVE}" -ne 0 ]] && { log "FAILED: archivedb backup"; ((FAILED++)); }

if [[ "${FAILED}" -gt 0 ]]; then
    echo "${FAILED} database backup(s) failed on ${HOSTNAME}. Check ${LOGFILE}." \
        | mail -s "Parallel Backup Failure: ${HOSTNAME}" "${ALERT_EMAIL}"
    exit 1
fi

log "All database backups completed successfully"
```

```bash
chmod 700 /usr/local/sbin/parallel-backup.sh
```

The `wait <PID>` call blocks until the specified background process exits and returns its exit code. By waiting for each PID individually and capturing the exit codes, the script correctly detects which jobs succeeded and which failed, even when they run concurrently.

## Retry Logic for Transient Failures

Not all job failures warrant an immediate alert and human intervention. Network timeouts, temporary resource unavailability, and brief service disruptions are often transient — retrying the job a few minutes later succeeds without any human involvement. Building retry logic into scheduled jobs reduces unnecessary alert noise and improves reliability.

### A Retry Wrapper

```bash
nano /usr/local/sbin/with-retry.sh
```

```bash
#!/bin/bash
# with-retry.sh
# Runs a command with configurable retry logic.
# Usage: with-retry.sh <max_attempts> <delay_seconds> <command> [args...]

MAX_ATTEMPTS="$1"
DELAY="$2"
shift 2
COMMAND="$@"
LOGFILE="/var/log/scheduling/retries.log"

mkdir -p "$(dirname "${LOGFILE}")"
log() { echo "[$(date '+%Y-%m-%d %H:%M:%S')] $*" | tee -a "${LOGFILE}"; }

ATTEMPT=1
while [[ "${ATTEMPT}" -le "${MAX_ATTEMPTS}" ]]; do
    log "Attempt ${ATTEMPT}/${MAX_ATTEMPTS}: ${COMMAND}"
    eval "${COMMAND}"
    EXIT_CODE=$?

    if [[ "${EXIT_CODE}" -eq 0 ]]; then
        log "Success on attempt ${ATTEMPT}"
        exit 0
    fi

    log "Failed on attempt ${ATTEMPT} (exit code: ${EXIT_CODE})"

    if [[ "${ATTEMPT}" -lt "${MAX_ATTEMPTS}" ]]; then
        log "Retrying in ${DELAY} seconds"
        sleep "${DELAY}"
    fi

    ((ATTEMPT++))
done

log "All ${MAX_ATTEMPTS} attempts failed for: ${COMMAND}"
exit 1
```

```bash
chmod 700 /usr/local/sbin/with-retry.sh
```

Use it in crontab entries or scripts:

```
# Retry the remote transfer up to 3 times, waiting 5 minutes between attempts
30 3 * * *  root  /usr/local/sbin/with-retry.sh 3 300 /usr/local/sbin/remote-transfer.sh
```

### Exponential Backoff

For transient failures caused by external service overload, exponential backoff — waiting progressively longer between retries — is more respectful of the failing service than fixed-delay retries:

```bash
nano /usr/local/sbin/with-backoff.sh
```

```bash
#!/bin/bash
# with-backoff.sh
# Runs a command with exponential backoff retry.
# Usage: with-backoff.sh <max_attempts> <initial_delay_seconds> <command> [args...]

MAX_ATTEMPTS="$1"
INITIAL_DELAY="$2"
shift 2
COMMAND="$@"
LOGFILE="/var/log/scheduling/retries.log"

mkdir -p "$(dirname "${LOGFILE}")"
log() { echo "[$(date '+%Y-%m-%d %H:%M:%S')] $*" | tee -a "${LOGFILE}"; }

ATTEMPT=1
DELAY="${INITIAL_DELAY}"

while [[ "${ATTEMPT}" -le "${MAX_ATTEMPTS}" ]]; do
    log "Attempt ${ATTEMPT}/${MAX_ATTEMPTS} (delay was ${DELAY}s): ${COMMAND}"
    eval "${COMMAND}"
    EXIT_CODE=$?

    if [[ "${EXIT_CODE}" -eq 0 ]]; then
        log "Success on attempt ${ATTEMPT}"
        exit 0
    fi

    log "Failed (exit code: ${EXIT_CODE})"

    if [[ "${ATTEMPT}" -lt "${MAX_ATTEMPTS}" ]]; then
        log "Backing off for ${DELAY} seconds"
        sleep "${DELAY}"
        DELAY=$(( DELAY * 2 ))
    fi

    ((ATTEMPT++))
done

log "All ${MAX_ATTEMPTS} attempts failed"
exit 1
```

```bash
chmod 700 /usr/local/sbin/with-backoff.sh
```

With an initial delay of 60 seconds and 4 attempts, the delays would be 60, 120, and 240 seconds — a total wait of 7 minutes before declaring final failure.

## Timeout Enforcement

Long-running jobs that hang indefinitely — waiting for a network connection that never comes, blocked on a locked database table, or stuck in an infinite loop — can prevent subsequent runs from starting and leave resources locked. Enforcing a timeout ensures jobs either complete or fail within a bounded time.

### Using timeout

The `timeout` command runs a command and kills it if it has not completed within the specified duration:

```bash
timeout 2h /usr/local/sbin/system-backup.sh
```

If the backup does not complete within 2 hours, `timeout` sends SIGTERM to the process. After a grace period (default 10 seconds), it sends SIGKILL if the process has not exited. `timeout` exits with code 124 when it kills a process due to timeout, making it easy to detect in scripts:

```bash
timeout 2h /usr/local/sbin/system-backup.sh
EXIT_CODE=$?

if [[ "${EXIT_CODE}" -eq 124 ]]; then
    echo "Backup timed out after 2 hours" | mail -s "Backup Timeout" admin@example.com
elif [[ "${EXIT_CODE}" -ne 0 ]]; then
    echo "Backup failed with exit code ${EXIT_CODE}" | mail -s "Backup Failed" admin@example.com
fi
```

In systemd service units, `TimeoutStartSec=` serves the same purpose:

```ini
[Service]
Type=oneshot
ExecStart=/usr/local/sbin/system-backup.sh
TimeoutStartSec=2h
```

When the timeout expires, systemd sends SIGTERM followed by SIGKILL and records the failure in the journal.

## Scheduling Across Multiple Servers

When the same job needs to run on multiple servers but only once across all of them — for example, a job that processes a shared work queue — naive parallel scheduling causes every server to attempt the work simultaneously. Several patterns address this.

### Leader Election with a Shared Lock File

For a small number of servers sharing an NFS mount, a shared lock file implements basic leader election: whichever server acquires the lock first does the work; the others skip their run:

```bash
nano /usr/local/sbin/shared-job.sh
```

```bash
#!/bin/bash
# shared-job.sh
# Runs a job only on the server that acquires the shared NFS lock.
# Other servers skip their run gracefully.

SHARED_LOCKFILE="/mnt/shared/locks/shared-job.lock"
LOGFILE="/var/log/scheduling/shared-job.log"
HOSTNAME=$(hostname -s)

mkdir -p "$(dirname "${LOGFILE}")"
log() { echo "[$(date '+%Y-%m-%d %H:%M:%S')] [${HOSTNAME}] $*" | tee -a "${LOGFILE}"; }

(
    flock -n 200 || {
        log "Lock not acquired — another server is running this job"
        exit 0
    }

    log "Lock acquired — running job"
    /usr/local/sbin/process-shared-queue.sh
    EXIT_CODE=$?
    log "Job completed with exit code ${EXIT_CODE}"
    exit "${EXIT_CODE}"

) 200>"${SHARED_LOCKFILE}"
```

```bash
chmod 700 /usr/local/sbin/shared-job.sh
```

Schedule on all servers via cron:

```
0 2 * * *  root  /usr/local/sbin/shared-job.sh
```

Whichever server's cron job runs first and acquires the NFS lock does the work. The others find the lock held and exit cleanly. When the winning server finishes, the lock is released — but since the job should only run once per cycle, the others have already exited and will not retry until the next scheduled run.

:::warning
NFS locking requires the `rpc.lockd` and `rpc.statd` services to be running on both the NFS client and server. On AlmaLinux, these are managed by `nfs-utils`. Verify NFS locking is functional before relying on it for job coordination in production.
:::

## Environment Management for Complex Jobs

Enterprise jobs often need consistent, well-defined environments. Rather than relying on the shell environment at invocation time or setting variables in crontabs, managing the environment in dedicated files makes it explicit and auditable.

### EnvironmentFile in systemd Services

For systemd-managed jobs, the `EnvironmentFile=` directive reads key-value pairs from a file:

```bash
nano /etc/myapp/scheduler-env
```

```
DATABASE_URL=postgresql://appuser:password@db01.example.com/myapp
API_ENDPOINT=https://api.example.com/v2
BACKUP_DESTINATION=/backup/myapp
LOG_LEVEL=info
```

```bash
chmod 600 /etc/myapp/scheduler-env
```

Reference it in the service unit:

```ini
[Service]
Type=oneshot
EnvironmentFile=/etc/myapp/scheduler-env
ExecStart=/opt/myapp/bin/scheduled-task.sh
```

The environment file is only readable by root (permissions `600`), which protects credentials it may contain. The service runs with those variables available to the script.

### Environment Validation

For jobs where missing environment variables would cause silent incorrect behaviour (such as writing to the wrong database or sending to the wrong API endpoint), validate required variables at the start of the script:

```bash
#!/bin/bash
# Validate required environment variables before proceeding

REQUIRED_VARS=(DATABASE_URL API_ENDPOINT BACKUP_DESTINATION)
MISSING=()

for VAR in "${REQUIRED_VARS[@]}"; do
    [[ -z "${!VAR}" ]] && MISSING+=("${VAR}")
done

if [[ "${#MISSING[@]}" -gt 0 ]]; then
    echo "Missing required environment variables: ${MISSING[*]}" >&2
    exit 1
fi

# Proceed with the actual job
```

This pattern catches misconfiguration early, producing a clear error message rather than a confusing downstream failure.

## Scheduling Observability

In complex scheduling environments, knowing the state of all scheduled jobs — which ran, which failed, which are currently running — requires more than checking individual log files. Centralizing scheduling observability makes it manageable.

### A Scheduling Log Aggregator

Standardize all scheduled job logging to a common format so a single query can show the state of all jobs:

```bash
nano /usr/local/sbin/job-wrapper.sh
```

```bash
#!/bin/bash
# job-wrapper.sh
# Wraps a scheduled job with standardized logging to a central scheduler log.
# Usage: job-wrapper.sh <job_name> <command> [args...]

JOB_NAME="$1"
shift
COMMAND="$@"
SCHEDULER_LOG="/var/log/scheduling/jobs.log"
HOSTNAME=$(hostname -s)

mkdir -p "$(dirname "${SCHEDULER_LOG}")"

START_TIME=$(date '+%Y-%m-%d %H:%M:%S')
START_EPOCH=$(date +%s)

echo "${START_TIME} START   ${HOSTNAME} ${JOB_NAME}" >> "${SCHEDULER_LOG}"

eval "${COMMAND}"
EXIT_CODE=$?

END_TIME=$(date '+%Y-%m-%d %H:%M:%S')
END_EPOCH=$(date +%s)
DURATION=$(( END_EPOCH - START_EPOCH ))

STATUS="SUCCESS"
[[ "${EXIT_CODE}" -ne 0 ]] && STATUS="FAILED(${EXIT_CODE})"

echo "${END_TIME} ${STATUS} ${HOSTNAME} ${JOB_NAME} duration=${DURATION}s" \
    >> "${SCHEDULER_LOG}"

exit "${EXIT_CODE}"
```

```bash
chmod 700 /usr/local/sbin/job-wrapper.sh
```

Use it in crontab entries:

```
0 2 * * *  root  /usr/local/sbin/job-wrapper.sh "system-backup" /usr/local/sbin/system-backup.sh
0 3 * * *  root  /usr/local/sbin/job-wrapper.sh "remote-transfer" /usr/local/sbin/remote-transfer.sh
*/5 * * * *  root  /usr/local/sbin/job-wrapper.sh "health-check" /usr/local/sbin/check-services.sh
```

The central log produces a clear timeline of all job executions:

```
2024-06-01 02:00:01 START   web01 system-backup
2024-06-01 02:43:17 SUCCESS web01 system-backup duration=2596s
2024-06-01 03:00:01 START   web01 remote-transfer
2024-06-01 03:12:44 SUCCESS web01 remote-transfer duration=763s
```

This format is easy to grep, parse, and monitor. A query for recent failures:

```bash
grep "FAILED" /var/log/scheduling/jobs.log | tail -20
```

A query for jobs that have not run recently:

```bash
grep "system-backup" /var/log/scheduling/jobs.log | tail -1
```

## Integration with External Automation Platforms

For organizations running enterprise automation platforms, AlmaLinux's local scheduling tools can integrate with or be replaced by centralized schedulers.

**Ansible AWX / Red Hat Ansible Automation Platform** provides centralized job scheduling across all managed hosts, with role-based access control, credential management, and job history. Local cron jobs can be migrated to AWX job templates with scheduling, providing a single pane of glass for all automation across the infrastructure.

**Apache Airflow** is a workflow scheduler well-suited to complex DAG (Directed Acyclic Graph) dependencies — jobs where the execution order depends on the success or failure of multiple upstream tasks. For environments with complex data pipeline dependencies, Airflow's dependency management is far more expressive than shell chaining or systemd unit dependencies.

**Jenkins** is primarily a CI/CD platform but its pipeline scheduling and dependency features make it viable for general enterprise job scheduling, particularly in development-oriented environments.

For most AlmaLinux environments, the tools described in this page — flock, systemd dependencies, retry wrappers, shared NFS locks — are sufficient without introducing an external platform. External platforms become worthwhile when the number of jobs, their interdependencies, or the need for centralized visibility across many servers exceeds what local tooling can manage cleanly.

## Summary

Enterprise scheduling on AlmaLinux extends basic cron and systemd timer scheduling with patterns that address the reliability, coordination, and observability requirements of production environments. Job locking with `flock` prevents concurrent execution. Systemd `OnSuccess=` and shell `&&` chaining implement job dependencies. Retry wrappers with configurable delays reduce alert noise from transient failures. Shared NFS locks coordinate work across multiple servers. Central scheduling logs provide a unified view of job execution.

Key points to remember:

- Use `flock -n` (non-blocking) for scheduled jobs — skip rather than queue when the lock is held
- File descriptor 200 is the conventional choice for flock in subshells: `( flock -n 200 || exit; ... ) 200>lockfile`
- `Type=oneshot` systemd services are inherently protected against concurrent activation by the same timer
- `OnSuccess=` in a service unit activates a dependent service only when the prerequisite exits cleanly
- Use `wait <PID>` after background jobs to collect individual exit codes in parallel execution patterns
- `timeout 2h <command>` exits with code 124 on timeout — check for this specifically in error handling
- Standardize job logging format across all scheduled tasks to enable unified monitoring
- NFS locking for multi-server coordination requires `rpc.lockd` to be running on both client and server
