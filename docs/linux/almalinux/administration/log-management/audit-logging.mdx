# Audit Logging on AlmaLinux

The Linux Audit system provides a mechanism for tracking security-relevant events at the kernel level. Unlike application logs or the systemd journal, audit logs are generated by the kernel itself — before any userspace process can intercept or suppress them. This makes the audit subsystem the authoritative source for events like file access, system calls, privilege escalation, user authentication, and changes to critical configuration files.

On AlmaLinux, the audit daemon (`auditd`) is installed and enabled by default. It receives audit records from the kernel, writes them to `/var/log/audit/audit.log`, and provides tools for querying and reporting on that data. Understanding how to configure audit rules and interpret audit output is essential for security monitoring and compliance with frameworks like PCI DSS, HIPAA, and CIS Benchmarks.

---

## How the Audit System Works

The Linux Audit system has two main components: a kernel component that generates audit records, and the userspace daemon (`auditd`) that receives and stores them.

When an auditable event occurs — a file is opened, a system call is made, a user logs in — the kernel generates an audit record and places it in a kernel buffer. `auditd` reads from this buffer continuously and writes records to the audit log. Because the kernel generates these records, they cannot be suppressed by the process being audited, even if that process runs as root.

Audit rules define which events the kernel should generate records for. Without any rules configured, only a small set of events (login/logout, system startups and shutdowns) are recorded by default. You add rules to broaden coverage to match your security or compliance requirements.

The audit record format is structured but dense. Each record contains a type identifier, a timestamp, and a series of key-value pairs describing the event. Multiple records are often grouped into an event — for example, a file access event may include a `SYSCALL` record, a `PATH` record, and a `PROCTITLE` record, all sharing the same audit event ID.

## Managing auditd

### Checking Status

Verify that auditd is running and enabled at boot:

```bash
systemctl status auditd
```

To check whether the audit subsystem is active at the kernel level:

```bash
auditctl -s
```

The output includes `enabled 1` if auditing is active, the current PID of auditd, and counts of loaded rules and lost records. A non-zero `lost` count indicates that the kernel buffer overflowed and records were discarded — this may require tuning the buffer size.

### Starting, Stopping, and Reloading

auditd handles signals differently from most systemd services. You should use `service` rather than `systemctl` to stop or restart it, because systemctl sends SIGTERM which auditd interprets as a request to disable auditing rather than stop the daemon:

```bash
service auditd restart
service auditd stop
service auditd start
```

To reload configuration and rules without restarting the daemon:

```bash
service auditd reload
```

:::warning
Using `systemctl stop auditd` or `systemctl restart auditd` on AlmaLinux will stop auditing at the kernel level, not just the daemon. Always use the `service` command to manage auditd to avoid accidentally disabling the audit subsystem.
:::

## Audit Configuration

The main auditd configuration file is `/etc/audit/auditd.conf`. It controls where and how audit records are stored, what happens when the disk fills up, and how the daemon handles errors.

Open the file to review or adjust settings:

```bash
nano /etc/audit/auditd.conf
```

Key parameters to be aware of:

| Parameter | Default | Description |
|---|---|---|
| `log_file` | `/var/log/audit/audit.log` | Path to the audit log file |
| `max_log_file` | `8` | Maximum size in MB per log file |
| `max_log_file_action` | `ROTATE` | Action when max size is reached (`ROTATE`, `KEEP_LOGS`, `SUSPEND`, `HALT`) |
| `num_logs` | `5` | Number of rotated log files to keep |
| `space_left` | `75` | MB of free space at which to trigger `space_left_action` |
| `space_left_action` | `SYSLOG` | Action when space is low (`SYSLOG`, `EMAIL`, `SUSPEND`, `HALT`) |
| `admin_space_left_action` | `SUSPEND` | Action at critically low disk space |
| `disk_full_action` | `SUSPEND` | Action when disk is completely full |

The `HALT` action stops the system entirely when disk space runs out. This is the safest setting for high-security environments where losing audit records is unacceptable, but it is aggressive for general use. The `SUSPEND` action stops writing audit records without halting the system — less disruptive, but means events go unrecorded.

After changing `auditd.conf`, reload the daemon:

```bash
service auditd reload
```

## Managing Audit Rules

Audit rules are defined in `/etc/audit/rules.d/` as `.rules` files. On startup, `augenrules` compiles all files in this directory into a single ruleset and loads it. You can also load rules temporarily using `auditctl` directly — these take effect immediately but do not persist across reboots.

### Rule Syntax

There are three types of audit rules:

**Control rules** configure the audit system itself. For example, to set the kernel audit buffer size to 8192 records:

```
-b 8192
```

**File watch rules** monitor access to specific files or directories. The basic form is:

```
-w <path> -p <permissions> -k <key>
```

Where `-p` specifies which access types to watch (`r` = read, `w` = write, `x` = execute, `a` = attribute change) and `-k` assigns a searchable tag to matching events.

**System call rules** trigger on specific system calls, optionally filtered by user, process, or argument values. The basic form is:

```
-a <action>,<filter> -S <syscall> -F <field>=<value> -k <key>
```

Where `-a always,exit` is the most common action/filter combination, `-S` names the system call, `-F` adds field filters, and `-k` assigns a tag.

### Viewing Currently Loaded Rules

To see all rules currently active in the kernel:

```bash
auditctl -l
```

To see the rules as they would be compiled from `/etc/audit/rules.d/`:

```bash
augenrules --check
```

### Writing Persistent Rules

Create rule files in `/etc/audit/rules.d/`. The naming convention matters: files are loaded in alphabetical order, and it is conventional to prefix them with numbers to control ordering. The file `99-finalize.rules` typically contains the `-e 2` directive that locks the ruleset.

A well-organized rule directory might look like:

```
/etc/audit/rules.d/
├── 10-base-config.rules
├── 20-file-access.rules
├── 30-system-calls.rules
├── 40-privilege-escalation.rules
├── 99-finalize.rules
```

To apply changes after editing rule files:

```bash
augenrules --load
```

## Common Audit Rules

### Monitoring Critical Files

Watching important configuration files for any modification is a fundamental audit requirement. The following rules track writes and attribute changes on common sensitive files:

```bash
nano /etc/audit/rules.d/20-file-access.rules
```

```
# Monitor passwd and shadow files
-w /etc/passwd -p wa -k identity
-w /etc/shadow -p wa -k identity
-w /etc/group -p wa -k identity
-w /etc/gshadow -p wa -k identity

# Monitor sudoers
-w /etc/sudoers -p wa -k sudoers
-w /etc/sudoers.d/ -p wa -k sudoers

# Monitor SSH configuration
-w /etc/ssh/sshd_config -p wa -k sshd_config

# Monitor audit configuration itself
-w /etc/audit/ -p wa -k audit_config
-w /etc/audit/audit.rules -p wa -k audit_config
```

The `-k` key values are arbitrary tags you choose. They are used with `ausearch -k <key>` to quickly retrieve all events matching that tag. Choosing consistent, descriptive key names makes searching much easier later.

### Monitoring Login and Authentication Events

Login events are recorded automatically, but you can add explicit watches to supplement them:

```bash
nano /etc/audit/rules.d/25-login.rules
```

```
# Track failed and successful logins
-w /var/log/faillog -p wa -k login
-w /var/log/lastlog -p wa -k login
-w /var/log/tallylog -p wa -k login

# Monitor PAM configuration changes
-w /etc/pam.d/ -p wa -k pam_config
```

### Monitoring Privilege Escalation

Tracking use of `sudo` and changes in privilege level:

```bash
nano /etc/audit/rules.d/40-privilege-escalation.rules
```

```
# Log all sudo usage
-w /usr/bin/sudo -p x -k sudo_exec

# Monitor su usage
-w /bin/su -p x -k su_exec

# Track setuid and setgid execution
-a always,exit -F arch=b64 -S execve -C uid!=euid -F euid=0 -k setuid_exec
-a always,exit -F arch=b32 -S execve -C uid!=euid -F euid=0 -k setuid_exec
```

The last two rules use `-C uid!=euid` (compare filter) to catch executions where the real user ID differs from the effective user ID — the hallmark of setuid program execution. Both 32-bit (`b32`) and 64-bit (`b64`) architectures are specified because on a 64-bit system, 32-bit system calls use a different call table.

### Monitoring System Call Activity

System call rules are the most powerful and the most verbose. Use them selectively to avoid overwhelming log volume.

To track all file deletions by non-root users:

```bash
nano /etc/audit/rules.d/30-system-calls.rules
```

```
# Track file deletions
-a always,exit -F arch=b64 -S unlink -S unlinkat -S rename -S renameat -F auid>=1000 -F auid!=4294967295 -k file_deletion
-a always,exit -F arch=b32 -S unlink -S unlinkat -S rename -S renameat -F auid>=1000 -F auid!=4294967295 -k file_deletion
```

The filter `-F auid>=1000` limits these rules to regular users (UIDs 1000 and above). The filter `-F auid!=4294967295` excludes processes that were not initiated by a logged-in user (4294967295, or `0xffffffff`, is the value used when no login UID is set).

To track changes to system time:

```
# Monitor time changes
-a always,exit -F arch=b64 -S adjtimex -S settimeofday -S clock_settime -k time_change
-a always,exit -F arch=b32 -S adjtimex -S settimeofday -S clock_settime -k time_change
-w /etc/localtime -p wa -k time_change
```

To track loading and unloading of kernel modules:

```
# Monitor kernel module changes
-w /sbin/insmod -p x -k module_load
-w /sbin/rmmod -p x -k module_load
-w /sbin/modprobe -p x -k module_load
-a always,exit -F arch=b64 -S init_module -S delete_module -k module_load
```

### Locking the Ruleset

The `-e 2` directive locks the audit ruleset so it cannot be modified while the system is running, even by root. This prevents an attacker who has gained root access from disabling auditing to cover their tracks. Place this at the end of your rules, in a file that sorts last:

```bash
nano /etc/audit/rules.d/99-finalize.rules
```

```
# Lock the audit configuration
-e 2
```

:::warning
Once `-e 2` is active, audit rules cannot be changed without rebooting. Only add this directive when you are confident your ruleset is correct and complete. During initial configuration and testing, leave it out until you are satisfied with your rules.
:::

After creating or modifying rule files, load them:

```bash
augenrules --load
```

Verify the rules are active:

```bash
auditctl -l
```

## Querying Audit Logs with ausearch

`ausearch` is the primary tool for searching the audit log. It understands the audit record format and can reconstruct multi-record events, filter by time, user, key, and many other fields.

### Searching by Key

The key tag defined in your rules is the fastest way to retrieve relevant events:

```bash
ausearch -k identity
```

This returns all audit events tagged with the `identity` key — in the example rules above, any write or attribute change on `/etc/passwd`, `/etc/shadow`, `/etc/group`, or `/etc/gshadow`.

### Searching by Time

To search within a time range, use `--start` and `--end`:

```bash
ausearch --start today
ausearch --start "06/01/2024 08:00:00" --end "06/01/2024 10:00:00"
```

Time expressions can be natural language (`today`, `yesterday`, `recent`) or explicit timestamps in `MM/DD/YYYY HH:MM:SS` format.

### Searching by User

To find all audit events associated with a specific user (by login name):

```bash
ausearch -ua alice
```

To search by numeric UID:

```bash
ausearch -ui 1001
```

### Searching by Event Type

To retrieve only events of a specific type:

```bash
ausearch -m USER_LOGIN
ausearch -m SYSCALL
ausearch -m USER_CMD
```

Common event types include `USER_LOGIN`, `USER_AUTH`, `USER_CMD` (sudo commands), `SYSCALL`, `PATH`, `CONFIG_CHANGE`, and `DAEMON_START`.

### Combining Filters

`ausearch` filters can be combined. To find all failed login attempts today:

```bash
ausearch -m USER_LOGIN --start today --success no
```

To find all sudo commands run by a specific user in the last 24 hours:

```bash
ausearch -k sudo_exec -ua alice --start yesterday
```

### Interpreting ausearch Output

A typical audit event for a sudo command looks like this:

```
----
time->Sat Jun  1 09:14:22 2024
type=USER_CMD msg=audit(1717229662.123:4521): pid=12345 uid=1001 auid=1001 ses=3 subj=unconfined_u:unconfined_r:unconfined_t:s0-s0:c0.c1023 msg='cwd="/home/alice" cmd="cat /etc/shadow" terminal=pts/1 res=success'
```

Key fields:

- `auid` — the audit UID, set at login and preserved across privilege changes; this is the original logged-in user
- `uid` — the effective UID at the time of the event
- `pid` — process ID
- `ses` — session ID
- `cmd` — the command that was executed
- `res` — whether the action succeeded (`success` or `failed`)

The `auid` field is particularly important. Even if a user runs `sudo su` and then executes commands as root, the `auid` still reflects the original login identity — which is why it is more reliable than `uid` for attribution.

To make `ausearch` output more readable, the `-i` flag interprets numeric values into human-readable names:

```bash
ausearch -k identity -i
```

This translates UIDs to usernames, syscall numbers to names, and so on.

## Reporting with aureport

While `ausearch` retrieves specific events, `aureport` generates summary reports across the entire audit log. It is useful for getting a high-level picture of audit activity.

### Summary Report

To get an overall summary of audit activity:

```bash
aureport
```

This shows counts of various event types: logins, failed logins, commands, files accessed, and so on.

### Login Report

To see a report of all login events:

```bash
aureport -l
```

To see only failed logins:

```bash
aureport -l --failed
```

### Authentication Report

```bash
aureport -au
```

This lists authentication attempts with user, terminal, result, and timestamp.

### Command Report

To see all commands executed via sudo or su:

```bash
aureport -c
```

### File Access Report

```bash
aureport -f
```

This summarizes which files were accessed and by whom.

### Time-Bounded Reports

All `aureport` reports accept `--start` and `--end` flags:

```bash
aureport -l --start today
aureport --start "06/01/2024 00:00:00" --end "06/01/2024 23:59:59"
```

### Anomaly Report

The `-a` flag generates an anomaly report, highlighting events that may indicate unusual or suspicious activity:

```bash
aureport -a
```

## Predefined Rulesets for Compliance

Rather than writing all rules from scratch, AlmaLinux ships with predefined rule sets aligned to common compliance frameworks. These are located in `/usr/share/audit/sample-rules/`:

```bash
ls /usr/share/audit/sample-rules/
```

Notable rulesets include:

| File | Purpose |
|---|---|
| `10-base-config.rules` | Basic audit system configuration |
| `30-stig.rules` | Rules aligned to DISA STIG requirements |
| `30-nispom.rules` | Rules for NISPOM compliance |
| `30-pci-dss-v31.rules` | PCI DSS v3.1 aligned rules |
| `30-ospp.rules` | Common Criteria OSPP profile rules |

To use a predefined ruleset, copy the relevant files to `/etc/audit/rules.d/`:

```bash
cp /usr/share/audit/sample-rules/30-stig.rules /etc/audit/rules.d/
augenrules --load
```

Review the copied file before loading it — some rules generate very high log volume and may not be appropriate for all environments. Adjust or comment out rules that are not relevant to your use case.

:::tip
The STIG and OSPP rulesets are a good starting point for most environments, even if you are not pursuing formal compliance certification. They represent a well-considered set of security-relevant events that cover the most important audit categories.
:::

## Log Rotation for Audit Logs

auditd handles its own log rotation internally, configured via `auditd.conf` with the `max_log_file`, `max_log_file_action`, and `num_logs` parameters described earlier. You should not use logrotate for `/var/log/audit/audit.log` — doing so can cause auditd to lose its file handle and stop writing records.

To check the current size and rotation status of audit logs:

```bash
ls -lh /var/log/audit/
```

Rotated files are named `audit.log.1`, `audit.log.2`, and so on. `ausearch` and `aureport` search only the current `audit.log` by default. To include rotated logs, use the `-if` flag to specify a file, or search across all files:

```bash
ausearch -k identity -if /var/log/audit/audit.log.1
```

## Summary

The Linux Audit system on AlmaLinux provides kernel-level tracking of security-relevant events that cannot be suppressed by userspace processes. `auditd` collects these records and writes them to `/var/log/audit/audit.log`. Audit rules define which events are captured, and the `ausearch` and `aureport` tools enable effective querying and reporting.

Key points to remember:

- Use `service auditd restart` rather than `systemctl` to avoid disabling the audit subsystem
- Define rules in `/etc/audit/rules.d/` and apply them with `augenrules --load`
- Always specify both `b64` and `b32` architecture variants for system call rules on 64-bit systems
- Use meaningful `-k` key tags on every rule to make `ausearch` filtering effective
- The `auid` field reliably identifies the original logged-in user even after privilege changes
- Add `-e 2` to lock the ruleset only after rules are tested and confirmed correct
- Use predefined rulesets from `/usr/share/audit/sample-rules/` as a starting point for compliance
- Do not use logrotate for audit logs — auditd manages its own rotation via `auditd.conf`
