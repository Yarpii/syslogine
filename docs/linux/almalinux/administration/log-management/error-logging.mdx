# Error Logging on AlmaLinux

Error logs are the primary diagnostic resource when something goes wrong on a Linux system. Understanding where errors are recorded, what they look like, and how to interpret them efficiently is one of the most practical skills a system administrator can develop. On AlmaLinux, errors surface across several distinct layers — the kernel, the systemd journal, rsyslog-managed files, and individual application logs — each with its own format, location, and tooling.

This page covers where different categories of errors are recorded, how to find and read them effectively, how to distinguish between severity levels, and how to manage error log volume so that important messages do not get buried in noise.

---

## Where Errors Are Recorded

Error messages on AlmaLinux do not all go to a single place. Knowing which layer an error originates from determines where to look first.

**Kernel errors** are generated by the kernel itself — hardware faults, driver failures, filesystem errors, out-of-memory events, and similar low-level problems. They appear in the kernel ring buffer (accessible via `dmesg`) and are forwarded to the systemd journal and rsyslog.

**Systemd and service errors** are produced by systemd and the services it manages. They go to the systemd journal and are queryable with `journalctl`. This includes failed service starts, unit dependency errors, and process exit codes.

**rsyslog-managed errors** are written to traditional log files under `/var/log/`. The most important are `/var/log/messages` (general system messages) and `/var/log/secure` (authentication errors). rsyslog receives these from the kernel and from applications that use the syslog API.

**Application-specific errors** are written directly to files by applications that manage their own logging. Common examples include Apache writing to `/var/log/httpd/error_log`, PostgreSQL writing to `/var/log/postgresql/`, and custom applications writing to wherever they are configured. These do not go through rsyslog or the journal unless the application is explicitly configured to do so.

The following table summarizes common error sources and their locations:

| Error source | Primary location |
|---|---|
| Kernel hardware/driver errors | `dmesg`, `journalctl -k`, `/var/log/messages` |
| OOM killer events | `dmesg`, `/var/log/messages` |
| Filesystem errors | `dmesg`, `/var/log/messages` |
| systemd service failures | `journalctl -u <unit>` |
| Boot errors | `journalctl -b` |
| Authentication failures | `/var/log/secure` |
| Cron job errors | `/var/log/cron` |
| Package manager errors | `/var/log/dnf.log` |
| SELinux denials | `/var/log/audit/audit.log`, `journalctl` |
| Apache errors | `/var/log/httpd/error_log` |
| Postfix errors | `/var/log/maillog` |

## Syslog Severity Levels

The syslog standard defines eight severity levels, used consistently across rsyslog, the systemd journal, and most applications that log via syslog. Understanding these levels helps you filter noise from signal.

| Level | Keyword | Meaning |
|---|---|---|
| 0 | `emerg` | System is unusable; immediate action required |
| 1 | `alert` | Action must be taken immediately |
| 2 | `crit` | Critical condition; component has failed |
| 3 | `err` | Error condition; operation failed |
| 4 | `warning` | Warning; something unexpected happened but the system is still functioning |
| 5 | `notice` | Normal but significant event worth noting |
| 6 | `info` | Informational; routine operational messages |
| 7 | `debug` | Debug output; verbose detail for development purposes |

In practice, the levels you will most often act on are `err` (3) and above. `warning` (4) often warrants monitoring but not immediate action. `info` (6) and `debug` (7) are useful during troubleshooting but generate too much volume to monitor continuously.

## Kernel Errors

### Reading the Kernel Ring Buffer

The kernel maintains a circular buffer of its own messages. `dmesg` reads from this buffer and is the fastest way to see recent kernel activity:

```bash
dmesg
```

The output can be long. To see only the most recent entries:

```bash
dmesg | tail -30
```

To filter for error-level messages only, `dmesg` supports a level filter since kernel 3.5:

```bash
dmesg --level=err,crit,alert,emerg
```

To display timestamps in human-readable format rather than seconds since boot:

```bash
dmesg -T
```

To follow new kernel messages in real time (useful during hardware diagnostics or when reproducing an issue):

```bash
dmesg -w
```

### Common Kernel Error Patterns

**Hardware errors** often appear as lines referencing specific devices or memory addresses. A disk I/O error looks like:

```
[12345.678] blk_update_request: I/O error, dev sda, sector 1234567
[12345.679] Buffer I/O error on dev sda1, logical block 12345, async page read
```

This pattern indicates a failing disk or bad sectors. The device name (`sda`) and sector number help identify the affected drive and region.

**Out-of-memory (OOM) events** occur when the system runs out of memory and the kernel kills a process to recover it:

```
[23456.789] Out of memory: Kill process 4567 (mysqld) score 892 or sacrifice child
[23456.790] Killed process 4567 (mysqld) total-vm:2048000kB, anon-rss:1024000kB
```

The `score` value indicates how aggressively the OOM killer targeted that process. A high score means the process was using a large amount of memory relative to other processes. Repeated OOM kills indicate that the system is consistently memory-constrained and needs either more RAM, a larger swap partition, or reduced memory usage from the identified process.

**Filesystem errors** appear when the kernel detects corruption or unexpected conditions in a mounted filesystem:

```
[34567.890] EXT4-fs error (device sda1): ext4_find_entry:1455: inode #2: comm bash: reading directory lblock 0
```

Filesystem errors should be taken seriously. They can indicate disk failure, filesystem corruption, or a kernel bug. If you see these, plan to run `fsck` on the affected filesystem at the next maintenance window.

### Kernel Errors in the Journal

Because the systemd journal also captures kernel messages, you can use `journalctl` with the `-k` flag and priority filter to retrieve kernel errors:

```bash
journalctl -k -p err
```

This is often more convenient than `dmesg` because the journal persists across reboots and supports time-based filtering:

```bash
journalctl -k -p err --since "2024-06-01"
```

## Service and systemd Errors

### Finding Failed Services

The fastest way to see which services have failed is:

```bash
systemctl --failed
```

This lists all units currently in a failed state. For each failed unit, `systemctl status` gives you the immediate cause:

```bash
systemctl status nginx
```

The output includes the exit code, a signal if the process was killed, and the last several lines of journal output for that unit. In most cases, this is enough to identify the problem without a separate `journalctl` query.

### Querying Service Errors in the Journal

For a deeper look at a service's error history, use `journalctl` filtered by unit and priority:

```bash
journalctl -u nginx -p err
```

To see everything the service logged since the last boot, including informational messages that provide context around errors:

```bash
journalctl -u nginx -b
```

To watch a service's log output in real time while you attempt to reproduce or fix a problem:

```bash
journalctl -f -u nginx
```

### Understanding Exit Codes and Signals

When a service fails, systemd records how the process ended. The `systemctl status` output shows either an exit code or a signal:

- `code=exited, status=1` — the process exited with a non-zero return code, indicating an error it detected itself
- `code=killed, signal=SEGV` — the process was killed by the kernel due to a segmentation fault (memory access error)
- `code=killed, signal=KILL` — the process was forcibly killed, either by the OOM killer or a manual `kill -9`
- `code=killed, signal=TERM` — the process received a termination signal, which could be intentional (systemctl stop) or unexpected

A segmentation fault (`SEGV`) almost always indicates a bug in the application or a corrupted library. An OOM kill (`KILL` from the kernel) indicates memory pressure. Distinguishing between these is important because the remediation is completely different.

### Boot Errors

Boot errors are often the most difficult to diagnose because the system may not be fully operational when they occur. The journal from the previous boot is accessible even after a successful reboot:

```bash
journalctl -b -1 -p err
```

To see the last entries from a previous boot — what was happening just before the system went down:

```bash
journalctl -b -1 -n 100
```

If the system crashed or lost power unexpectedly, the journal from the last boot may be incomplete, but what is recorded is still valuable.

## rsyslog Error Files

### /var/log/messages

`/var/log/messages` is the general system log and receives messages from many sources. By default, rsyslog writes messages at `info` level and above here, which means it includes a lot of routine output alongside genuine errors.

To extract only error-level messages from this file:

```bash
grep -E " (emerg|alert|crit|err|error): " /var/log/messages
```

Because the exact keyword varies by application (some write `err`, some write `error`, some write `ERROR`), using a case-insensitive match is more reliable for broad searches:

```bash
grep -i "error\|critical\|failed\|failure" /var/log/messages
```

For time-bounded searches, note that each line in `/var/log/messages` begins with a timestamp in the format `Mon DD HH:MM:SS`. To extract messages from a specific hour:

```bash
grep "^Jun  1 09:" /var/log/messages
```

### /var/log/secure

Authentication errors are written to `/var/log/secure`. The most common entries are failed SSH logins, PAM authentication failures, and sudo errors:

```bash
grep "error\|failed\|failure" /var/log/secure
```

To see authentication errors from the current day only:

```bash
grep "^$(date '+%b %e')" /var/log/secure | grep -i "error\|failed"
```

### Configuring rsyslog to Separate Error Logs

By default, errors at all severity levels above `debug` go into `/var/log/messages` mixed with informational output. For environments where you want errors to be written to a dedicated file for easier monitoring, you can add an rsyslog rule.

Create a drop-in configuration file:

```bash
nano /etc/rsyslog.d/errors.conf
```

```
# Write all messages at err level and above to a dedicated file
*.err /var/log/system-errors.log
```

After saving, restart rsyslog:

```bash
systemctl restart rsyslog
```

From this point on, any message at `err` severity or above — from any facility — will also be written to `/var/log/system-errors.log`. This file becomes a single, focused location for error monitoring tools or scripts to watch.

:::tip
If you configure a dedicated error log file, make sure to add a logrotate rule for it as well. Error log files can grow quickly on systems experiencing problems, and an unmanaged file can fill the disk. See the [Log Rotation](./log-rotation) page for configuration details.
:::

## Application-Specific Error Logs

Applications that manage their own logging write errors in their own formats to their own locations. The approach for reading these varies by application, but some common patterns apply.

### Apache / HTTPD

Apache writes errors to `/var/log/httpd/error_log`. Each line includes a timestamp, severity level, process ID, client address (for request-related errors), and message:

```
[Sat Jun 01 09:00:00.123456 2024] [core:error] [pid 1234] [client 192.168.1.10:54321] File does not exist: /var/www/html/favicon.ico
```

The severity level appears in square brackets after the module name (`[core:error]`). To filter for errors and above:

```bash
grep "\[error\]\|\[crit\]\|\[alert\]\|\[emerg\]" /var/log/httpd/error_log
```

Apache's error log level is configured in `/etc/httpd/conf/httpd.conf` with the `LogLevel` directive. Setting it to `warn` reduces volume significantly while retaining meaningful error output.

### PostgreSQL

PostgreSQL writes log output to `/var/log/postgresql/` (if configured to do so) or to the systemd journal. Each log line includes a severity prefix:

```
2024-06-01 09:00:00 UTC [1234] ERROR:  relation "nonexistent_table" does not exist
```

To extract only errors from a PostgreSQL log file:

```bash
grep "^[0-9-]* [0-9:]* UTC \[[0-9]*\] ERROR:" /var/log/postgresql/postgresql.log
```

If PostgreSQL logs to the journal, retrieve its output with:

```bash
journalctl -u postgresql -p err
```

### Application Logs Without a Standard Format

Many custom applications write logs in their own format without following syslog conventions. In these cases, the application's documentation defines what constitutes an error line. The general approach is still `grep` with keywords relevant to that application's error vocabulary — `ERROR`, `FATAL`, `Exception`, `Traceback`, and so on.

For applications that write multi-line error messages (such as Java stack traces), `grep -A` is useful to capture the lines following an error marker:

```bash
grep -A 20 "Exception\|FATAL" /var/log/myapp/application.log
```

This shows 20 lines after each match, which is typically enough to capture a full stack trace.

## Correlating Errors Across Sources

Some problems manifest across multiple log sources simultaneously, and understanding the sequence of events requires correlating entries from different files or subsystems. The key challenge is that timestamps may not be perfectly synchronized across sources, especially if the system clock was adjusted or if log entries come from multiple hosts.

When investigating a problem that spans sources, work backwards from the visible symptom. If a service is down, start with `systemctl status` and `journalctl -u <service>`, then check `/var/log/messages` for kernel or system-level events at the same time, then check application logs if applicable.

To compare timestamps across different log sources, normalize them to a common format. The journal uses ISO 8601 timestamps internally; rsyslog log files use a shorter format. When correlating, note that rsyslog file timestamps omit the year, which can cause confusion when looking at rotated logs from the previous year.

To view journal output with full timestamps in a format that matches syslog files:

```bash
journalctl -u sshd -o short-iso
```

The `short-iso` output format uses `YYYY-MM-DDTHH:MM:SS` timestamps, which are unambiguous and easier to compare with other sources.

## Reducing Error Log Noise

On a busy system, the volume of log output can make it difficult to notice genuine errors among routine messages. Several approaches help reduce noise without losing important information.

### Adjusting Application Log Levels

Many applications write at `debug` or `info` level by default, generating far more output than is useful in production. Check the documentation for each application to find how to raise the minimum log level. For Apache, this is `LogLevel warn` in `httpd.conf`. For most Java applications, it is a logging configuration file (log4j, logback, etc.) where individual loggers can be set to `WARN` or `ERROR`.

### Filtering rsyslog Output

rsyslog can be configured to drop messages matching specific patterns before they are written to files, using property-based filters. To discard a known noisy but harmless message:

```bash
nano /etc/rsyslog.d/filter-noise.conf
```

```
# Discard a known harmless repeated message from ntpd
:msg, contains, "kernel time sync status change" stop
```

The `stop` action discards the message without writing it anywhere. Place this rule before the rules that write to log files, so the message is dropped before it reaches the output actions.

:::warning
Be careful when filtering out log messages. It is easy to accidentally suppress a message that would later be important for diagnosing a problem. Only filter messages you are confident are genuinely harmless and will never be needed for troubleshooting. Document every filter you add with a comment explaining why it was added.
:::

### Using journalctl Priority Filtering in Daily Work

Getting into the habit of filtering by priority in day-to-day log checks reduces the time spent reading noise. A useful starting point for a morning health check:

```bash
journalctl -p warning --since yesterday
```

This shows all warnings and above from all sources since the previous day. It is a quick way to catch problems that occurred overnight without reading through thousands of informational lines.

## Summary

Error logging on AlmaLinux spans multiple layers: the kernel ring buffer, the systemd journal, rsyslog-managed files, and application-specific logs. Effective error management means knowing which layer to consult for which type of problem, how to filter by severity to surface relevant messages, and how to correlate events across sources when a problem affects multiple components.

Key points to remember:

- Use `dmesg --level=err,crit,alert,emerg` or `journalctl -k -p err` for kernel-level errors
- Use `systemctl --failed` and `systemctl status <unit>` as the first step for service failures
- Distinguish between exit codes and signals to understand why a service process ended
- `/var/log/messages` and `/var/log/secure` are the primary rsyslog targets for system and auth errors
- A dedicated `/var/log/system-errors.log` via rsyslog makes automated monitoring simpler
- Use `grep -i` with multiple error keywords for application logs that do not follow syslog conventions
- Use `-A` with `grep` to capture multi-line error output such as stack traces
- Raise application log levels in production to reduce noise without losing error visibility
- Document any rsyslog message filters thoroughly to avoid accidentally suppressing useful output
