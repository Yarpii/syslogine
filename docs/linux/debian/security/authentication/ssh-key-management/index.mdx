# SSH Key Management

SSH keys replace passwords with asymmetric cryptography. Your private key never leaves your machine — the server only ever sees your public key. But generating a key is just the beginning. This guide covers everything from key generation internals to certificate authorities, KDF hardening, `authorized_keys` restrictions, and rotation strategies that most guides never touch.

:::info Prerequisites
- Debian 11 (Bullseye) or Debian 12 (Bookworm)
- OpenSSH installed: `sudo apt install openssh-client openssh-server`
- Basic familiarity with the terminal
:::

---

## 1. Understanding Key Types

Before generating a key, understand the differences. Not all key types are equal.

| Algorithm | Key size | Speed | Security | Use when |
|-----------|----------|-------|----------|----------|
| **Ed25519** | 256-bit (fixed) | Fastest | Excellent | Always — modern default |
| **ECDSA** | 256/384/521-bit | Fast | Good | Avoid — NIST curves have design concerns |
| **RSA** | 2048–4096-bit | Slower | Good (4096) | Legacy systems only |
| **DSA** | 1024-bit (fixed) | — | Broken | Never — deprecated since OpenSSH 7.0 |

### Why Ed25519 over RSA?

Ed25519 uses **Curve25519**, designed by Daniel Bernstein with verifiable, auditable constants — unlike NIST P-256 used by ECDSA, where the curve constants have no documented mathematical origin (a concern among cryptographers since the Snowden disclosures). Ed25519 keys are also much shorter, making `authorized_keys` files cleaner and operations faster.

:::warning ECDSA and NIST curves
Avoid ECDSA (`-t ecdsa`) in new deployments. The NIST curves are widely considered to have potentially backdoor-friendly constants. Ed25519 is the correct modern choice.
:::

## 2. Generating Keys — The Right Way

Always generate keys on your **local machine**, never on the server.

### Basic generation

```bash
ssh-keygen -t ed25519 -C "alice@laptop-2024"
```

The `-C` flag is a comment embedded in the public key. Use something meaningful — you will thank yourself when auditing `authorized_keys` files with dozens of keys months later. Good comments include the username, machine, and year: `alice@work-laptop-2024`.

### The -a flag: brute-force resistance for your private key

```bash
ssh-keygen -t ed25519 -a 100 -C "alice@laptop-2024"
```

The `-a` flag controls the **number of KDF (Key Derivation Function) rounds** used to derive the encryption key that protects your private key file on disk.

**What it actually does:**

When you set a passphrase, OpenSSH does not use your passphrase directly as the encryption key. It runs your passphrase through `bcrypt-pbkdf` N times (where N is the value you pass to `-a`) to derive the actual encryption key. More rounds = more computation per attempt = exponentially harder to brute-force.

| `-a` value | Unlock time (modern CPU) | Brute-force resistance |
|-----------|--------------------------|------------------------|
| 16 *(default)* | ~0.1 seconds | Low — attackers can try millions of passphrases/sec with GPUs |
| 64 | ~0.4 seconds | Moderate |
| **100** | ~0.6 seconds | **Good — recommended baseline** |
| 200 | ~1.2 seconds | Strong |
| 500 | ~3 seconds | Very strong — noticeable delay on slower machines |

The default of **16 rounds is dangerously low**. An attacker who steals your `id_ed25519` file can crack weak passphrases in hours using GPU tools. With 100 rounds, that same attack is 6x slower per attempt — and the delay is imperceptible to you when using `ssh-agent`.

:::tip
Use `-a 100` as your baseline. If the unlock delay bothers you, use `ssh-agent` — you enter the passphrase once and it stays in memory for the rest of your session.
:::

### Full recommended command

```bash
ssh-keygen -t ed25519 -a 100 -C "alice@laptop-$(date +%Y)"
```

For RSA on legacy systems:

```bash
ssh-keygen -t rsa -b 4096 -a 100 -C "alice@laptop-$(date +%Y)"
```

### Choosing a strong passphrase

- Minimum 20 characters
- Use a passphrase generated by a password manager — not a sentence you composed
- Never reuse a passphrase across different keys

## 3. Understanding the Key Files

After generation you have two files:

```
~/.ssh/id_ed25519      ← private key (NEVER share)
~/.ssh/id_ed25519.pub  ← public key (safe to share)
```

### What the private key actually contains

```bash
cat ~/.ssh/id_ed25519
```

```
-----BEGIN OPENSSH PRIVATE KEY-----
b3BlbnNzaC1rZXktdjEAAAAA...
-----END OPENSSH PRIVATE KEY-----
```

This is an OpenSSH-format private key. The key material is encrypted with AES-256-CTR, using a key derived from your passphrase via `bcrypt-pbkdf` with the number of rounds you set with `-a`. Without the passphrase, this file is useless to an attacker.

### What the public key contains

```bash
cat ~/.ssh/id_ed25519.pub
```

```
ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAA... alice@laptop-2024
```

Three space-separated fields: **algorithm**, **base64-encoded key material**, **comment**. This is what goes into `authorized_keys` on every server.

### Inspect key details without exposing the private key

```bash
# Show fingerprint and comment
ssh-keygen -lf ~/.ssh/id_ed25519.pub

# Show fingerprint in MD5 format (for older systems that display MD5)
ssh-keygen -lf ~/.ssh/id_ed25519.pub -E md5

# Show the randomart (visual fingerprint — useful for out-of-band verification)
ssh-keygen -lvf ~/.ssh/id_ed25519.pub
```

The **fingerprint** is what you compare with a server admin over a separate channel to confirm you have the right key — especially important on first connection.

## 4. Recover a Public Key from a Private Key

Lost your `.pub` file but still have the private key? Regenerate it:

```bash
ssh-keygen -y -f ~/.ssh/id_ed25519 > ~/.ssh/id_ed25519.pub
```

The `-y` flag reads the private key (prompting for the passphrase) and outputs the corresponding public key to stdout. This is also useful to verify that a public/private key pair actually belong together — if the output matches the `.pub` file, they match.

## 5. Change or Remove a Passphrase

Change the passphrase on an existing key without generating a new key pair:

```bash
ssh-keygen -p -f ~/.ssh/id_ed25519
```

Change passphrase and update the KDF rounds at the same time:

```bash
ssh-keygen -p -a 100 -f ~/.ssh/id_ed25519
```

Remove the passphrase entirely (for automation — use with caution):

```bash
ssh-keygen -p -f ~/.ssh/id_ed25519 -P "current-passphrase" -N ""
```

:::warning
Keys without passphrases should only exist in tightly controlled environments (e.g. internal CI/CD pipelines) where the private key file is stored in a secrets manager. On a developer laptop, always use a passphrase.
:::

## 6. File Permissions

SSH refuses to use files with overly permissive permissions. This is enforced by the client — not a recommendation.

```bash
# Local machine
chmod 700 ~/.ssh
chmod 600 ~/.ssh/id_ed25519
chmod 644 ~/.ssh/id_ed25519.pub
chmod 600 ~/.ssh/config

# Server
chmod 700 ~/.ssh
chmod 600 ~/.ssh/authorized_keys
chown -R $USER:$USER ~/.ssh
```

| File | Required permission | Why |
|------|--------------------|----|
| `~/.ssh/` | `700` | Directory must not be group/world readable |
| `id_ed25519` | `600` | Private key must be owner-read only |
| `id_ed25519.pub` | `644` | Public key can be world-readable |
| `authorized_keys` | `600` | Must not be group/world writable |
| `config` | `600` | Must not be group/world writable |

## 7. Deploying Public Keys to Servers

<Tabs>
  <TabItem value="ssh-copy-id" label="ssh-copy-id" default>

```bash
ssh-copy-id -i ~/.ssh/id_ed25519.pub user@server
```

`ssh-copy-id` appends the public key to `~/.ssh/authorized_keys`, creates the file and directory if they do not exist, and sets the correct permissions automatically.

With a custom port:

```bash
ssh-copy-id -i ~/.ssh/id_ed25519.pub -p 2222 user@server
```

  </TabItem>
  <TabItem value="manual" label="Manual (one-liner)">

```bash
cat ~/.ssh/id_ed25519.pub | ssh user@server \
  "mkdir -p ~/.ssh && chmod 700 ~/.ssh && cat >> ~/.ssh/authorized_keys && chmod 600 ~/.ssh/authorized_keys"
```

This is the manual equivalent of `ssh-copy-id` — useful when the tool is not available or when you are piping from a script.

  </TabItem>
  <TabItem value="loop" label="Multiple servers">

```bash
for server in server1 server2 server3; do
  ssh-copy-id -i ~/.ssh/id_ed25519.pub user@$server && echo "✓ $server" || echo "✗ $server"
done
```

## 8. The authorized_keys File — Deep Dive

The `authorized_keys` file is more powerful than most people realize. Each line is not just a public key — it can include options that tightly control what that key is allowed to do.

### Basic format

```
[options] keytype base64-key comment
```

### Restriction options

```bash
# Restrict to a specific source IP
from="203.0.113.10" ssh-ed25519 AAAA...key... alice@office

# Restrict to a CIDR range
from="10.0.0.0/8,192.168.1.0/24" ssh-ed25519 AAAA...key... alice@vpn

# Multiple IPs (comma-separated, no spaces)
from="203.0.113.10,203.0.113.11" ssh-ed25519 AAAA...key... alice@offices

# Wildcard hostname pattern
from="*.example.com" ssh-ed25519 AAAA...key... deploy@ci

# Restrict to a single command (key can ONLY run this, ignores what client sends)
command="/usr/bin/rsync --server -logDtprze.iLsfxCIvu . /backup" ssh-ed25519 AAAA...key... backup-script

# No interactive terminal (for automation keys)
no-pty ssh-ed25519 AAAA...key... deploy-pipeline

# Combine multiple restrictions
from="10.0.0.0/8",no-pty,no-port-forwarding,no-X11-forwarding,no-agent-forwarding ssh-ed25519 AAAA...key... ci-runner

# Key automatically expires on a specific date
expiry-time="20241231" ssh-ed25519 AAAA...key... alice@contractor
```

### Full options reference

| Option | Effect |
|--------|--------|
| `from="pattern"` | Restrict to source IP/hostname — supports CIDR, wildcards, comma-separated |
| `command="cmd"` | Only allow this specific command — client's requested command is ignored |
| `no-pty` | Prevents pseudo-terminal allocation (no interactive shell) |
| `no-port-forwarding` | Disables all TCP port forwarding |
| `no-X11-forwarding` | Disables X11 display forwarding |
| `no-agent-forwarding` | Disables SSH agent forwarding |
| `no-user-rc` | Prevents execution of `~/.ssh/rc` on login |
| `permitopen="host:port"` | Limits port forwarding to a specific destination only |
| `environment="VAR=val"` | Sets an environment variable for the session |
| `expiry-time="YYYYMMDD"` | Key stops working after this date — no manual revocation needed |
| `restrict` | Enables ALL restrictions, then selectively re-enable what you need |

### The restrict keyword

`restrict` is the safest baseline for automation or service keys — it disables everything, then you explicitly re-enable only what is required:

```bash
# Tunnel key that can only forward one specific port
restrict,permitopen="db.internal:5432" ssh-ed25519 AAAA...key... db-tunnel

# Deploy key that can only run one script
restrict,command="/usr/local/bin/deploy.sh" ssh-ed25519 AAAA...key... deploy-key

# Backup key with no shell at all
restrict,command="/usr/bin/rsync --server -az . /backups/" ssh-ed25519 AAAA...key... rsync-backup
```

## 9. The ~/.ssh/config Client File

The client config lets you define per-host connection parameters, avoiding long flags every time.

```bash
chmod 600 ~/.ssh/config
nano ~/.ssh/config
```

```bash
# Global defaults applied to all hosts
Host *
    AddKeysToAgent yes
    IdentitiesOnly yes
    ServerAliveInterval 60
    ServerAliveCountMax 3
    HashKnownHosts yes

# Production server
Host prod
    HostName 203.0.113.10
    User alice
    Port 2222
    IdentityFile ~/.ssh/id_ed25519_prod

# Internal server via bastion jump host
Host internal
    HostName 10.0.1.50
    User alice
    ProxyJump bastion

# Bastion host
Host bastion
    HostName bastion.example.com
    User alice
    IdentityFile ~/.ssh/id_ed25519_bastion

# Git services
Host github.com
    User git
    IdentityFile ~/.ssh/id_ed25519_git
```

`IdentitiesOnly yes` in the global block is critical — without it, SSH offers every key loaded in your agent, which can exhaust `MaxAuthTries` on hardened servers before trying the right key.

Connect with just:

```bash
ssh prod
ssh internal    # automatically tunnels through bastion
```

## 10. Managing ssh-agent

`ssh-agent` holds your decrypted private key in memory. You type the passphrase once per session, and the agent handles all subsequent authentications automatically.

```bash
# Start the agent (usually already running in desktop sessions)
eval "$(ssh-agent -s)"

# Add a key — prompts for passphrase once
ssh-add ~/.ssh/id_ed25519

# Add with time limit — key auto-expires from agent after 4 hours
ssh-add -t 4h ~/.ssh/id_ed25519

# List keys currently in the agent (fingerprints only)
ssh-add -l

# List keys with full public key output
ssh-add -L

# Remove a specific key from the agent
ssh-add -d ~/.ssh/id_ed25519

# Remove all keys
ssh-add -D
```

### Persistent agent on headless Debian servers

Add to `~/.bashrc` or `~/.profile`:

```bash
if [ -z "$SSH_AUTH_SOCK" ]; then
    eval "$(ssh-agent -s)"
    ssh-add ~/.ssh/id_ed25519
fi
```

## 11. known_hosts — Server Identity Verification

On first connection to a server, SSH shows a fingerprint and asks you to verify it:

```
The authenticity of host 'server (203.0.113.10)' can't be established.
ED25519 key fingerprint is SHA256:abc123...xyz.
Are you sure you want to continue connecting (yes/no)?
```

This is not a formality — it is your protection against **man-in-the-middle attacks**. Always verify the fingerprint out-of-band (server provider dashboard, colleague, etc.) before typing `yes`. Once accepted, the server's key is stored in `~/.ssh/known_hosts`.

### Managing known_hosts

```bash
# View all stored host keys
cat ~/.ssh/known_hosts

# Get a server's fingerprint before connecting (for out-of-band verification)
ssh-keyscan -H server.example.com | ssh-keygen -lf -

# Add a server's key to known_hosts without connecting interactively
ssh-keyscan -H server.example.com >> ~/.ssh/known_hosts

# Remove a specific host entry (e.g. after server rebuild)
ssh-keygen -R server.example.com
ssh-keygen -R 203.0.113.10

# Hash all plaintext hostnames in known_hosts
ssh-keygen -H
```

### Why hash known_hosts?

By default, `known_hosts` stores hostnames in plaintext. Anyone who reads the file immediately knows which servers you connect to. After hashing (`ssh-keygen -H`), hostnames are replaced with salted hashes. SSH can still verify servers (it hashes the connecting hostname and compares), but a leaked `known_hosts` file reveals nothing.

Add to `~/.ssh/config` to hash all future entries automatically:

```bash
Host *
    HashKnownHosts yes
```

## 12. SSH Certificate Authorities (Advanced)

Managing `authorized_keys` across many servers and users does not scale. If you have 20 servers and 10 engineers, that is 200 files to maintain. SSH certificates solve this cleanly.

**The concept:** Instead of deploying each user's public key to every server, you create a trusted Certificate Authority (CA). You sign user public keys with the CA. Servers trust the CA — so any user with a CA-signed certificate can log in without touching `authorized_keys`.

### Create a CA key pair

```bash
# Generate CA key — protect this like root credentials
ssh-keygen -t ed25519 -a 100 -f ~/.ssh/ssh_ca -C "SSH-CA-$(date +%Y)"
```

Keep the CA private key offline or in a hardware security module in production.

### Sign a user's public key

```bash
ssh-keygen -s ~/.ssh/ssh_ca \
  -I "alice@example.com" \
  -n alice,ubuntu \
  -V +52w \
  -z 1 \
  ~/.ssh/id_ed25519.pub
```

| Flag | Meaning |
|------|---------|
| `-s ~/.ssh/ssh_ca` | CA private key to sign with |
| `-I "alice@example.com"` | Certificate identity — shown in server logs |
| `-n alice,ubuntu` | Principals — which usernames this cert permits login as |
| `-V +52w` | Validity — expires in 52 weeks (`+1d`, `+4w`, `+1y` also work) |
| `-z 1` | Serial number — for audit logs and revocation |

This produces `~/.ssh/id_ed25519-cert.pub`. The user presents this certificate alongside their private key.

### Configure servers to trust the CA

```bash
# Copy CA public key to the server
sudo cp ~/.ssh/ssh_ca.pub /etc/ssh/trusted_user_ca_keys
sudo chmod 644 /etc/ssh/trusted_user_ca_keys
```

Add to `/etc/ssh/sshd_config`:

```bash
TrustedUserCAKeys /etc/ssh/trusted_user_ca_keys
```

```bash
sudo systemctl restart ssh
```

Now any user with a valid CA-signed certificate can log in — no `authorized_keys` needed on the server.

### Inspect a certificate

```bash
ssh-keygen -Lf ~/.ssh/id_ed25519-cert.pub
```

Shows the signing CA fingerprint, validity window, principals, serial number, and extensions.

### Revoke a certificate by serial number

```bash
# Build or update a Key Revocation List (KRL)
ssh-keygen -k -f /etc/ssh/revoked_keys -z 1 ~/.ssh/id_ed25519-cert.pub
```

Add to `sshd_config`:

```bash
RevokedKeys /etc/ssh/revoked_keys
```

The revoked certificate is immediately rejected on all servers that load this KRL — no need to touch `authorized_keys` on any individual machine.

## 13. Auditing SSH Keys on a Server

Regularly audit which keys have access — especially on shared or long-running servers:

```bash
# Find all authorized_keys files on the system
sudo find /home /root /etc -name "authorized_keys" 2>/dev/null

# Print fingerprint of every key across all authorized_keys files
sudo find /home /root -name "authorized_keys" 2>/dev/null | while read f; do
  echo "=== $f ===";
  while IFS= read -r line; do
    [[ "$line" =~ ^# ]] && continue
    [[ -z "$line" ]] && continue
    echo "$line" | ssh-keygen -lf /dev/stdin 2>/dev/null || echo "(unparseable) $line"
  done < "$f"
done

# Check when authorized_keys files were last modified
sudo find /home -name "authorized_keys" -printf "%TY-%Tm-%Td %p\n" | sort -r

# Find legacy DSA or short ECDSA keys that should be replaced
sudo grep -h "^ssh-dss\|^ecdsa-sha2-nistp256\b" /home/*/.ssh/authorized_keys 2>/dev/null
```

## 14. Key Rotation Strategy

Rotate keys when: a device is lost or stolen, an employee leaves, a key may have been exposed, or as part of a regular security policy (at minimum annually).

**Rule: never remove the old key until the new key is confirmed working.**

```bash
# 1. Generate a new key pair with hardened KDF
ssh-keygen -t ed25519 -a 100 -f ~/.ssh/id_ed25519_new -C "alice@laptop-$(date +%Y)"

# 2. Deploy the new public key — old key still works
ssh-copy-id -i ~/.ssh/id_ed25519_new.pub user@server

# 3. Test login with the new key in a SEPARATE terminal
ssh -i ~/.ssh/id_ed25519_new user@server echo "New key works"

# 4. Remove only the old key from authorized_keys on the server
# Filter out the old key by its comment, keep everything else
grep -v "alice@laptop-2023" ~/.ssh/authorized_keys > /tmp/ak_tmp \
  && mv /tmp/ak_tmp ~/.ssh/authorized_keys \
  && chmod 600 ~/.ssh/authorized_keys

# 5. Promote the new key to the default name
mv ~/.ssh/id_ed25519_new ~/.ssh/id_ed25519
mv ~/.ssh/id_ed25519_new.pub ~/.ssh/id_ed25519.pub
```

## 15. Separate Keys Per Purpose

Never reuse one key for everything. If it is compromised, everything it has access to is compromised.

```bash
ssh-keygen -t ed25519 -a 100 -f ~/.ssh/id_ed25519_personal  -C "alice@personal-$(date +%Y)"
ssh-keygen -t ed25519 -a 100 -f ~/.ssh/id_ed25519_work      -C "alice@work-$(date +%Y)"
ssh-keygen -t ed25519 -a 100 -f ~/.ssh/id_ed25519_git       -C "alice@git-$(date +%Y)"
ssh-keygen -t ed25519        -f ~/.ssh/id_ed25519_deploy     -N "" -C "deploy-pipeline-$(date +%Y)"
```

Wire them up per host in `~/.ssh/config` (see section 9). The deploy key has no passphrase because it lives in a secrets manager — but that is intentional and isolated.

## Troubleshooting

| Problem | Cause | Fix |
|---------|-------|-----|
| `Permission denied (publickey)` | Wrong permissions on `.ssh/` or `authorized_keys` | `chmod 700 ~/.ssh && chmod 600 ~/.ssh/authorized_keys` |
| `WARNING: UNPROTECTED PRIVATE KEY FILE` | Private key is world-readable | `chmod 600 ~/.ssh/id_ed25519` |
| `Too many authentication failures` | Agent tries all keys, hits `MaxAuthTries` | Add `IdentitiesOnly yes` to `~/.ssh/config` |
| Key ignored despite being in `authorized_keys` | `PubkeyAuthentication no` in `sshd_config` | Set `PubkeyAuthentication yes`, restart SSH |
| `WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED` | Server rebuilt or potential MITM | Verify fingerprint, then `ssh-keygen -R hostname` |
| `ssh-copy-id` fails (password auth disabled) | No password auth on server | Deploy manually via console |
| Certificate rejected | Expired, wrong principals, or revoked | Check with `ssh-keygen -Lf cert.pub` |

Always start debugging with:

```bash
ssh -vvv -i ~/.ssh/id_ed25519 user@server 2>&1 | head -80
```
